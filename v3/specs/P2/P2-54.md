# P2-54: Store: encryption survives a crash, no keychain in tests; resumed runs keep their start

Model: opus
Depends on: P2-51
Feature IDs: TR-09, SP-13; review follow-ups from P2-37 and P2-19

## Goal
Two follow-ups on store state that outlives a process.

Encryption (P2-37). `encrypt` stores the key before it swaps the file. A crash in between
leaves a key in Credential Manager and a plain database. Every later `encrypt` then refuses
("a database key already exists"), and the owner cannot finish. A crash after the swap but
before the shred leaves `alexia.db.plain`, the whole plain database, and nothing ever removes
it. Also, `Store::open` on a path that does not exist yet reads the keychain. Every test in
every crate that opens a fresh store therefore reaches the real Credential Manager. After this
task an interrupted `encrypt` can be finished, a plain leftover never outlives the next open,
and a test that does not ask for the keychain never touches it.

Resume (P2-19). `Trace::resume` writes the run's `at` as the resume time, so a resumed run
looks as if it started at the restart. It also checks that the live row exists and then
updates it in two steps. After this task a resumed run keeps its original start, and the check
and the update are one statement.

## Steps
1. A marker beside the database, `alexia.db.keyed`, says "this database is meant to be
   encrypted". It holds no secret, only a fixed line of text. `encrypt` writes it, with fsync,
   before it stores the key.
2. `Store::open` (db.rs about line 107): for a path that does not exist, look up the key only
   when the marker exists. No marker means a new plain database, with no keychain read. For an
   encrypted file, read the key as today. For a plain file with the marker and a stored key, an
   `encrypt` was cut short: open it plain as today and `tracing::warn!` once that encryption
   did not finish and `alexia-hub encrypt` will finish it.
3. `Store::open` of an encrypted file: if `alexia.db.plain` exists, shred it with the same
   `shred` `encrypt` uses (make it `pub(crate)`), and its `-wal`/`-shm` too. Log one warning
   that names the file, never its content.
4. `encrypt` (encrypt.rs about line 41): when the database is plain, a key is stored and the
   marker exists, this is a resume. Use the stored key instead of refusing. If the stored key is
   not 64 hex digits, refuse as today. Without the marker, a stored key still refuses, so
   `refuses_twice` keeps its meaning. If `encrypt` finds the database already encrypted and a
   `.plain` beside it, shred the leftover before it refuses.
5. On an `export_and_swap` error with no swap, remove the marker together with the key. On a
   resume, keep the stored key: it was the owner's before this call.
6. `live_touch` returns `Ok(changed == 1)`. `Trace::resume` (trace.rs about line 103) calls it
   once and refuses when it returns false, with the same sentence as today. It no longer calls
   `live_runs()` first.
7. `Trace::open` takes the run's start time. A new run passes `now_ms()`. A resumed run passes
   the live row's `started_at`, read with `live_runs()` after the touch succeeded (a read, so
   it opens no new window). The resume note's own `at` stays the resume time.
