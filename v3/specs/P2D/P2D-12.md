# P2D-12: PC actions proven; the hub runs in the owner's session

Model: opus
Depends on: P2D-04, P2D-05, P2D-06
Feature IDs: SP-01, TR-01, AC-10

## Goal
After this task the hub that Task Scheduler starts runs in the owner's desktop session (G1), and
a scripted test on this PC shows the agent doing through the window API what v2 did on the PC:
seeing windows, opening an app, typing and reading it back, a screenshot, reading a document in
a chosen folder, Open and Show in folder on a produced file, a question answered in the window,
and the plan progress for the pill (G9). It proves INVENTORY's PC-action section closed.

## Touch only these paths
- `v3/crates/alexia-hub/src/watchdog.rs`   (change: `task_xml`, `install`, and its in-file tests)
- `v3/crates/alexia-hub/Cargo.toml`   (change: `[features] pc-actions = []`, `[[test]] name = "pc_actions" required-features = ["pc-actions"]`)
- `v3/crates/alexia-hub/tests/pc_actions.rs`   (create)

## Must not touch
`main.rs`, `tests/common/mod.rs` (use its helpers as P2D-02 left them), every library crate,
`plugins/` (the test copies them into a scratch folder), `packages/`.

## Interfaces
Task Scheduler XML (`task_xml(exe, user)`):
- Triggers: `LogonTrigger` for `user` only (with the existing 1-minute repetition). The
  `BootTrigger` is removed: before sign-in there is no desktop to act on.
- Principal: `<LogonType>InteractiveToken</LogonType>`, `<RunLevel>LeastPrivilege</RunLevel>`.
- `install()` registers it with `schtasks /Create /TN <TASK_NAME> /XML <path> /F` and **no**
  `/RU`/`/RP` (an interactive-token task needs no stored password), then `/Run`.
- Settings unchanged otherwise (restart on failure, no time limit, `IgnoreNew`).
- With the hub already started by the app, the task's hub exits on the lock (P2D-01); that is
  expected and not a failure the restart loop should fight: `MultipleInstancesPolicy` stays
  `IgnoreNew` and the exit code for "already running" is 0.

`pc_actions.rs` (Windows only, `#![cfg(windows)]`, feature `pc-actions`):
- Starts `alexia-hub run` with `ALEXIA_V3_DATA` scratch, `ALEXIA_PLUGINS_DIR` = a scratch copy
  of the repo's plugin folders found by scanning `plugins/` for manifests that provide
  `computer.control`, `computer.screenshot` and `document.extract` (by capability, not by name),
  with `node_modules` junctioned as P2-40 does, and the fake provider from `common` scripting the
  model's tool calls. Tool names are read from the hub's tool list by capability
  (`_meta["alexia/provides"]`) so the test names no plugin.
- Before the turn, through the window API only: `POST /api/settings` turns on the computer
  plugin's input setting (the manifest key whose `type` is `toggle` and that its tools check,
  read from the manifest at test time), `POST /api/server {action:"trust"}` for the three
  plugins, `POST /api/permissions {roots:[<scratch docs folder>]}`.
- Scripted turn 1 (`POST /api/chat`): list windows → open Notepad → type `alexia p2d` → read the
  focused element's text → screenshot. Checks: a `notepad.exe` process whose main window title
  exists; the read text contains `alexia p2d`; the screenshot step's outcome has a PNG file
  (non-empty, PNG signature); at least one `step.progress` frame with `stages` (the plugin's
  `run_task`/plan path, or skip this check with a printed reason if the scripted calls do not
  produce stages).
- Scripted turn 2: `document.extract` on a `.docx` fixture in the chosen folder → text found.
- Scripted turn 3: a destructive call the gate asks about → an `ask` frame → `POST
  /api/approve {allowed:true}` → it runs; the same with `false` → it does not.
- Produced file: `POST /api/file {id, action:"reveal"}` answers `{ok:true}` and an
  `explorer.exe` process appears within 5 s.
- Cleanup: Notepad closed without saving (`taskkill /PID`), Explorer window left (owner's
  shell), scratch removed.

## Steps
1. Change `task_xml`/`install`; update the in-file tests.
2. Write `pc_actions.rs` as above; run it on this PC in the owner's session (not over SSH, not as
   SYSTEM) and paste its output in the report.
3. If a PC action fails because of the hub (not the test), fix it only if the fix is in a path
   this spec names; otherwise stop and report the gap with evidence.

- In `watchdog.rs`: `task_xml_logon_only_interactive` (no `BootTrigger`, `InteractiveToken`, the

- `pc_actions` (above): run with `cargo test -p alexia-hub --features pc-actions --test
  pc_actions -- --nocapture` on this PC.

## Notes for the worker
- Why: v2's `computer` plugin drives the desktop through PowerShell and UI Automation
  (`plugins/computer/windows.js`); in session 0 none of it reaches the screen.
- Security: the test turns on input and trust only in its own scratch data folder, never in
  `%LOCALAPPDATA%\AlexiaHub`. It never touches the owner's real hub, settings or keychain
  (in-memory secrets, `ALEXIA_SECRETS_IN_MEMORY=1`, as `common` does).
- Do not run `alexia-hub install` on the PC from this task; the owner decides (PHASE *Owner
  needs*). Test the XML and arguments as data.
- The invariant: no plugin id in Rust, tests included; find tools by capability.
- Windows: `Get-Process notepad` alternative in Rust: `tasklist /FI "IMAGENAME eq notepad.exe"
  /FO CSV` with `CREATE_NO_WINDOW`. Windows 11 Notepad is a packaged app whose process is still
  `notepad.exe`.
