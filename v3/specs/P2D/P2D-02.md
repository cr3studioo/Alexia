# P2D-02: Contract: record v2's answers, replay them against the hub

Model: sonnet
Depends on: P2D-01
Feature IDs: SP-01

## Goal
After this task every INVENTORY row has at least one recorded case: a request and v2's answer
(status, content type, and the JSON shape or the SSE frame sequence), recorded from v2 core
itself where it can run headless, or written from the serve.ts lines where it cannot. A replay
test starts the real `alexia-hub run` and sends each case to the window API, comparing shapes.
Cases start `"hub": "pending"` (skipped, but counted and listed); each area task flips its own
to `"answers"`. This is the test the phase is checked against.

## Interfaces
Case file (one per area; research cases live in `editor.json`, local-stats in `local_models.json`):
```json
{ "area": "state",
  "cases": [
    { "row": "A1",                       // INVENTORY row id, required
      "name": "state on a fresh data folder",
      "source": "v2" | "hand",           // hand: written from serve.ts, with "from": "serve.ts:1915-2041"
      "hub": "pending" | "answers",
      "request": { "method": "GET", "path": "/api/state", "query": {}, "body": null, "token": true, "host": "127.0.0.1" },
      "setup": ["fresh"],                // named fixtures the replay applies first, see below
      "response": { "status": 200, "type": "application/json",
                    "shape": <json shape>, "ignore": ["/messages/*/at"] },
      "stream": null | [ { "shape": <json shape> }, ... ]   // SSE frames in order, for C1
    } ] }
```
Shape: v2's JSON with every leaf replaced by its type name (`"string"`, `"number"`, `"bool"`,
`"null"`), objects by their key set, arrays by the shape of their first element (`[]` if empty).
`ignore` is a list of JSON pointers (`*` matches any key or index) left out of the comparison.
Matching rule: same status, same content type up to `;`, same key set at every object, same leaf
type, arrays compared elementwise up to the shorter. An optional v2 key (absent in some v2
answers, `...(x && {k})`) is listed under `"optional": ["/path"]` and may be absent.

Setup fixtures (`tests/contract.rs`), applied to a scratch `ALEXIA_V3_DATA` before the hub
starts: `fresh` (empty store), `chat` (one session with two messages), `plugins`
(`ALEXIA_PLUGINS_DIR` = the `mcp-fixture` folder used by `agent_e2e`, plus a fixture manifest
with settings and panel widgets of every v2 widget type, written into the scratch dir by the
test), `scripted` (the fake provider from `common` scripting one tool call then text).

`common/mod.rs` additions:
```rust
pub struct Window { pub port: u16, pub token: String }
pub fn window(data: &Path) -> Window;            // waits ≤ 20 s for window.json, GETs "/", reads the token from the page
pub fn call(w: &Window, method: &str, path: &str, body: Option<&serde_json::Value>) -> (u16, String, Vec<u8>); // status, content-type, body
```
(Blocking `reqwest` is not available; use a tokio runtime inside, as `common` already does.)

## Steps
1. `record-v2.mjs` (Node 22, no new npm dependency): builds nothing; needs `pnpm typecheck`
   output in `packages/core/dist`. Starts v2 core headless with `LOCALAPPDATA` and
   `ALEXIA_DATA_NAME` pointing at a scratch folder and `ALEXIA_PORT` set (read
   `packages/core/src/entry.ts` and `scripts/` for how `pnpm start` boots it without the Tauri
   vault; if v2 refuses to start without one, use an in-memory secret store as its own tests do),
   reads the token from `GET /`, replays a request list, writes the shapes into the case files.
   Secrets: none; provider keys stay unset.
2. Record every INVENTORY row v2 can answer in a scratch folder. For rows that need a model, a
   plugin, a GPU or a paired computer, write the case by hand from the serve.ts / compute/api.ts
   lines: `"source": "hand"`, `"from"` naming the lines. C1 gets at least: a plain answer, a
   tool step with progress, an `ask` then `/api/approve`, `423` while busy.
3. `contract.rs`: one `#[test] fn contract()` that loads every file, starts `alexia-hub run`
   once per setup set, replays every `"answers"` case, collects all mismatches (path, expected,
   got) and fails listing them; prints the count of pending cases per area.
4. Mark the gate rows (S1–S4) `"answers"`: P2D-01 already made them pass.

## Tests
- `contract` (as above): passes with every S row answering and all others pending.
- `shape_matcher_unit` (in `contract.rs`): optional keys, `ignore` with `*`, arrays of unequal
  length, a type mismatch reported with its pointer.
- `every_row_has_a_case`: reads `v3/specs/P2D/INVENTORY.md`, extracts row ids (`S1`…`T4`,
  excluding `T1`–`T3`, `T5`), and fails if any has no case (T4 is a case in `gate.json` replayed
  by P2D-13's own test, marked `"hub": "pending"` here).

## Notes for the worker
- Do not change v2 code to make it recordable. If a route cannot be reached headless, hand-write.
- Volatile values (times, ids, tokens, sizes, versions) are covered by shapes; only use `ignore`
  for keys whose *presence* varies run to run.
- SSE: v2 writes `data: <json>\n\n` (serve.ts 3671–3672). Record frames by their top-level key
  set; `delta` frames repeated in a row collapse to one with `"repeat": true`.
- Keep the files small: one case per distinct shape, not per value.
- This test runs in `cargo test --workspace`, so it must not need Node or a network: replay
  only; `record-v2.mjs` is run by hand.
