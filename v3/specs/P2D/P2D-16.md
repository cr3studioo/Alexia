# P2D-16: Computer plugin: focus that really works, and no typing into the wrong window

Model: opus
Depends on: none
Feature IDs: none (owner A-19 item 5: "it cannot even do stuff on my computer")

## Goal
P2D-12 proved that Alexia's PC actions work on this PC except bringing a window to the front:
`plugins/computer/windows.js` `focus` uses VB `AppActivate`, which Windows' foreground lock
refuses for a background process (hub → node → powershell), and it still reports success. Every
later click, type or key step then goes to whatever window is in front, which is unsafe. After this
task, `focus` really brings the target window to the front on Windows 11, and typing, keys and
clicks refuse to act unless the window in front belongs to the process they target.

## Touch only these paths

- plugins/computer/test/windows.test.js   (change)

## Interfaces
- `focus(pid)` resolves only when the foreground window's process id is `pid` (or one of its
  child processes' top-level window, if v2 already treats it so), checked after the attempt with
  `GetForegroundWindow` + `GetWindowThreadProcessId`. Otherwise it rejects with a plain sentence:
  "Could not bring that window to the front." The tool answer says that sentence; it never says
  "Focused" when it did not.
- Make the attempt work under the foreground lock: restore the window if minimised, then the
  standard sequence: `AttachThreadInput` to the current foreground thread, `BringWindowToTop`,
  `SetForegroundWindow`, `SetFocus`, detach; if still not foreground, a synthetic Alt key down/up
  (the known unlock) and `SetForegroundWindow` once more. All through the existing PowerShell +
  Add-Type path the file already uses (no new npm dependency, no native addon).
- Guard: `type`, `key` and `click` take the target pid when the caller has one (the tools that
  follow an `open_app`/`focus` in the same task) and, right before sending input, check that the
  foreground window belongs to that pid; if not, they refuse with "The window in front is not the
  one I was working in, so I did not type." (or "click"), and send nothing. When no target pid is
  known (a plain screen click the owner asked for), behaviour stays as in v2.

## Steps
1. Read windows.js `focus`, `type`, `key`, `click` and how index.js calls them.
2. Implement the focus sequence and the foreground check above.
3. Thread the target pid through index.js only where a task step already knows its window.
4. Tests in windows.test.js for the parts that can be tested without the desktop: the generated
   PowerShell contains the foreground check and the unlock sequence; `focus` rejects when the
   checked pid differs (inject the check result the way the file's existing tests inject
   PowerShell output); `type`/`key`/`click` send nothing when the foreground pid differs.
5. A manual check on this PC, from PowerShell in the owner's session: open Character Map
   (charmap.exe) from a background process (a node script started by another node script is
   enough), call focus, confirm the foreground pid is Character Map's. Never type into, focus or
   close any window you did not open; close only the charmap process you started, by PID. Never
   use Notepad (it reopens the owner's unsaved tabs). Write what happened in the report.
