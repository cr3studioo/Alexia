# P2D-03: Core seam: the window's origin, structured progress, step frames, the window asker

Model: opus
Depends on: none
Feature IDs: SP-01, TR-01

## Goal
After this task core can tell the window what v2 told it: each tool step as it starts, its
progress with v2's `stages`, `plan`, `controls`, `preview` and `research` detail, its outcome
with files, notes, and permission questions. The window is its own origin, `Origin::Window`,
whose questions are asked in the window (through `WindowQuestions`) and whose slash commands
run, because it is the owner at the keyboard. Today `McpTooling` flattens progress to a line,
`DraftFrame` has only text frames, and Desktop questions go to Telegram (INVENTORY G6, G7).

Asker rule for `Origin::Window`: if `window.attached(run)` ask there (recorded in `approvals` like
any other, answered via `answer`); otherwise the primary chat, as Desktop does today.

## Steps
1. `Origin::Window`; fix every `match` on `Origin` in core, gateway, scheduler (Window acts like
   Desktop everywhere except commands and asking).
2. `commands::run`: allowed from `Origin::Channel` and `Origin::Window` (P2-73's reason was
   scheduled and plugin origins; the window is the owner).
3. `ToolProgress`: build it in `McpTooling` from the MCP progress notification and its `_meta`
   exactly as v2 `tooling.ts` 296–320 does (`alexia/preview` kept only if it starts
   `data:image/`, `alexia/stages` parsed as v2 `stagesOf`, `plan` only with stages,
   `alexia/controls` as `controlsOf`, `alexia/research` stored per (plugin, session) and attached
   as `research`). Telegram keeps using `line()`.
4. `Agent`: emit `Step` with `args` when a call starts, `Step` with `progress` per progress,
   `Step` with `outcome` when it ends; `Note` where v2 says a note (boundary acknowledgements,
   "Stopped before starting."); `Ask` is sent by `WindowQuestions::ask`, not by the agent.
5. Gateway: ignore `Step`, `Note`, `Ask` frames (Telegram shows what it shows today).
6. `WindowQuestions` and the asker rule.
