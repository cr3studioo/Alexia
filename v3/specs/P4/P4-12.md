# P4-12: McpHost: each call on the best device

Model: opus
Depends on: P4-11
Feature IDs: HB-09

## Goal
When more than one plugin or device answers a capability, the host asks a preference the hub
installs which provider to try first, instead of always taking the oldest install. A call can
also name a device. This is D-P4-9's mechanism; the policy lives in the hub (P4-37).

## Touch only these paths
- `v3/crates/alexia-mcp/src/host.rs`   (change: `set_prefer`, resolution order in `call_capability`, `answers`, `alexia/capability/call`, `alexia/compute/run`)
- `v3/crates/alexia-mcp/tests/prefer.rs`   (create)

## Must not touch
`lib.rs` (P4-11 is done with it), `call_capability_all`'s order (fan-out keeps resolution order),
other crates.

## Interfaces
```rust
/// Given a capability and its providers in resolution order, return them in the order to try.
pub type Prefer = Arc<dyn Fn(&str, &[PluginId]) -> Vec<PluginId> + Send + Sync>;
impl McpHost {
    pub fn set_prefer(&self, prefer: Prefer);
    /// As `call_capability`, but only providers whose `HostedTool.device` is `device`
    /// (`"hub"` = local plugins). Err NoProvider if that device has none online.
    pub async fn call_capability_on(&self, cap: &str, device: &str, args: Map<String, Value>, ctx: CallCtx) -> Result<types::CallToolResult, CallError>;
}
```
- `call_capability` tries providers in `prefer` order; a provider that is `Stopped` because its
  device is offline is skipped (never dialled in the call path more than once per 30 s).
- A `device` key in a capability call's arguments (from a plugin's `alexia/capability/call`) is
  removed from the arguments and routes like `call_capability_on`.
- `alexia/compute/run` (INTERFACES §3.4, "V3-4 paired") follows the same order.
- With no `prefer` set, behaviour is exactly today's.

## Steps
1. Store `prefer` in `Inner` behind a `RwLock<Option<Prefer>>`.
2. Apply it in the one place providers are ordered for single calls.
3. Offline skip using P4-11's state.
