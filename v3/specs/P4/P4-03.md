# P4-03: Store migration 5: devices, fallback sync, guests

Model: opus
Depends on: none
Feature IDs: HB-02, HB-11, HB-18, TR-11

## Goal
Core's database learns about paired devices, about turns the Mac answered while the hub was off
(so they are appended exactly once), and about guests. Migration 5 adds three tables and a small
API in a new file, so `db.rs` is left alone.

## Touch only these paths
- `v3/crates/alexia-store/src/migrations.rs`   (change: migration 5)
- `v3/crates/alexia-store/src/devices.rs`   (create: `impl Store` for the three tables)
- `v3/crates/alexia-store/src/types.rs`   (change: row types)
- `v3/crates/alexia-store/src/lib.rs`   (change: `mod devices;`, re-exports)
- `v3/crates/alexia-store/tests/devices.rs`   (create)

## Must not touch
`src/db.rs`, `src/import.rs`, migrations 1–4 (never edit an applied migration), other crates.

## Interfaces
Migration 5 (SQL, inside one transaction like the others):
```sql
CREATE TABLE devices (
  id TEXT PRIMARY KEY, name TEXT NOT NULL, endpoint TEXT NOT NULL UNIQUE,
  role TEXT NOT NULL CHECK (role IN ('hub','limb')), platform TEXT NOT NULL,
  hello TEXT NOT NULL,            -- the Hello JSON as received
  hints TEXT NOT NULL DEFAULT '{}', -- connect's hints JSON
  paired_at INTEGER NOT NULL, last_seen INTEGER, revoked_at INTEGER);
CREATE TABLE fallback_sync (
  device TEXT NOT NULL, remote_id INTEGER NOT NULL, local_id INTEGER NOT NULL,
  at INTEGER NOT NULL, PRIMARY KEY (device, remote_id));
CREATE TABLE guests (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, channel TEXT NOT NULL, chat TEXT,
  code_hash TEXT,                  -- sha256 of the one-time code until used, then NULL
  added_at INTEGER NOT NULL, removed_at INTEGER, UNIQUE (channel, chat));
```
Rust (in `types.rs`, re-exported):
```rust
pub struct DeviceRow { pub id: String, pub name: String, pub endpoint: String, pub role: String, pub platform: String,
                       pub hello: serde_json::Value, pub hints: serde_json::Value, pub paired_at: Ms, pub last_seen: Option<Ms>, pub revoked_at: Option<Ms> }
pub struct GuestRow { pub id: i64, pub name: String, pub channel: String, pub chat: Option<String>, pub added_at: Ms, pub removed_at: Option<Ms> }
impl Store {
    /// Insert, or re-pair: an existing row with the same endpoint is replaced and un-revoked.
    pub fn device_put(&self, d: &DeviceRow) -> Result<()>;
    pub fn devices(&self) -> Result<Vec<DeviceRow>>;            // not revoked, by name
    pub fn device(&self, id: &str) -> Result<Option<DeviceRow>>;
    pub fn device_by_endpoint(&self, endpoint: &str) -> Result<Option<DeviceRow>>;
    pub fn device_seen(&self, id: &str, at: Ms) -> Result<()>;
    pub fn device_hints(&self, id: &str, hints: &serde_json::Value) -> Result<()>;
    pub fn device_revoke(&self, id: &str, at: Ms) -> Result<bool>;
    /// The local id a fallback row became, if it was synced already.
    pub fn fallback_synced(&self, device: &str, remote_id: i64) -> Result<Option<i64>>;
    pub fn fallback_mark(&self, device: &str, remote_id: i64, local_id: i64, at: Ms) -> Result<()>;
    /// A guest with a one-time code; returns the row id. The code itself is never stored.
    pub fn guest_add(&self, name: &str, channel: &str, code_hash: &str, at: Ms) -> Result<i64>;
    /// The guest whose unused code hashes to `code_hash` on `channel` claims `chat`; the code is spent.
    pub fn guest_claim(&self, channel: &str, code_hash: &str, chat: &str) -> Result<Option<GuestRow>>;
    pub fn guest_of(&self, channel: &str, chat: &str) -> Result<Option<GuestRow>>; // not removed
    pub fn guests(&self) -> Result<Vec<GuestRow>>;
    pub fn guest_remove(&self, id: i64, at: Ms) -> Result<bool>;
}
```

## Steps
1. Add migration 5 after 4, following `migrations.rs`' pattern and its version check.
2. Write `devices.rs` with the API; JSON columns use `serde_json` as `db.rs` does elsewhere.
3. Re-export the row types.

## Notes for the worker
- The database is SQLCipher (TR-09); tests open it the way `tests/store.rs` does.
- Times are `Ms`. Ids of fallback messages come from the Mac's own store (INTERFACES §8.6).
- No secret goes into a table: the guest code is hashed with `sha2` (already a store dep? if not,
  hash in the caller and take the hash here, as the signature says).
