# P4-36: Limb: wake the PC, then the fallback brain

Model: opus
Depends on: P4-07, P4-14, P4-33, P3-16, P3-36
Feature IDs: HB-11, HB-10

## Goal
When the Mac's limb loses the hub, it first tries to wake the PC with a Wake-on-LAN packet. If
the hub is still gone after that, the Mac answers the owner on Telegram itself, with free cloud
models, the Mac's own plugins and the recent messages the hub pushed down, until the hub comes
back (D-P4-6). It keeps every fallback turn in its own store for the hub to collect (P4-40).

## Interfaces
Watcher (all times config, defaults):
```
hub reachable   = a link is open, or a `send_op(Presence)` succeeded in the last 60 s
lost for 30 s   → wol::wake(hub.hello.wake MACs)   (once per outage, again after 10 min)
lost for 120 s after the wake → fallback starts      (FALLBACK_AFTER_MS = 120_000)
hub reachable again, or Telegram answers 409 Conflict → fallback stops within 30 s
```
Fallback brain (inside the limb process): `Store` = the limb's; `Router` with the free providers
whose keys are in this Mac's keychain (`secret` names as the hub's: `provider_<id>`); `Agent` with
`AgentParts` whose tools are the limb's own `McpHost` tools, whose `Ask` refuses everything
(D-P4-6: anything needing approval answers "I'll do that when the PC is back."), no scheduler, no
memory plugin calls; the gateway with only the Telegram channel (token `_core.telegram_bot_token`
from this Mac's keychain). With no token or no provider key it does not start, and `status` says why.
Context: the hub pushes the last 50 messages of each owner chat through the tool
`fallback.context {chat, messages:[{role, text, at}]}` (hidden, called by the hub every 10 min and
on each turn end; P4-40 is the caller); the brain seeds a fallback session per chat with them.
Turns made in fallback are stored in the limb's store as normal sessions and messages, and
exposed through hidden tools `fallback.turns {after_id?}` → `{turns:[{id, chat, role, text, at}]}`
and `fallback.ack {up_to_id}` (deletes acknowledged ones). The first fallback reply in a chat
starts with "(The PC is off, so I'm answering from the Mac with less to go on.)".

## Steps
1. Rebase on P3-16 and P3-36 (AgentParts and Asker as they are then).
2. `watch.rs` as a small state machine with an injectable clock and `wake` function.
3. `fallback.rs`: build the pieces as the hub's `run` does (INTERFACES §2.6 order), minus what D-P4-6 leaves out.
4. The three hidden tools in `serve.rs`.

## Notes for the worker
- Split brain: only Telegram runs in fallback, and Telegram's 409 is the lock. Never poll while a
  link to the hub is open.
- The Mac's keys are set on the Mac (PHASE *Owner needs* 4); never sent over the mesh.
- Builds on macOS: no Windows-only crates; the Credential Manager code in `alexia-store` already
  uses `keyring`, which works on macOS.
