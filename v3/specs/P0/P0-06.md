# P0-06: Store: secrets in Credential Manager

Model: opus
Depends on: P0-05
Feature IDs: SP-18

## Goal
After this task `alexia_store::secrets` reads and writes plugin and core secrets in Windows
Credential Manager (macOS Keychain on the Mac) under v2's names, so `password` settings work for
v2 plugins and a Windows machine that ran v2 may already resolve its secrets. It also settles
INTERFACES.md §8.7: whether `keyring` 4 reads what v2 wrote.

## Touch only these paths
- `v3/crates/alexia-store/Cargo.toml`   (change: `keyring.workspace = true`)
- `v3/crates/alexia-store/src/lib.rs`   (change: `pub mod secrets;`)
- `v3/crates/alexia-store/src/secrets.rs`   (create)
- `v3/crates/alexia-store/tests/secrets.rs`   (create)
- `v3/Cargo.lock`   (change)

## Must not touch
`db.rs`, `namespace.rs`, other crates, `scripts/keychain-check*` (read them, don't change them),
anything in `packages/`.

## Interfaces
From INTERFACES.md §2.1:

```rust
pub mod secrets {
    /// Service "alexia", account "<owner>.<key>", where owner is a plugin id or "_core".
    /// Never logged, never cached by callers.
    pub fn get(owner: &str, key: &str) -> super::Result<Option<String>>;
    pub fn set(owner: &str, key: &str, secret: &str) -> super::Result<()>;
    pub fn delete(owner: &str, key: &str) -> super::Result<()>;            // missing entry is Ok
    pub fn delete_all(owner: &str, keys: &[String]) -> super::Result<()>;
}
```

Defined here, for tests and CI (no real keychain on a CI runner may be usable):

```rust
/// When set (any value), secrets live in a process-local map instead of the OS keychain.
/// Tests and CI only; the hub never sets it.
pub const MEMORY_BACKEND_ENV: &str = "ALEXIA_SECRETS_IN_MEMORY";
```

Errors: a keychain failure → `Error::Keychain("The system keychain could not be read.")` (or
"written"/"cleared"). The underlying error text goes to `tracing::debug!` only after checking it
contains no part of the secret; the `Error` never carries the secret.

## Steps
1. Add `keyring` (workspace, `4.2`). Pick the platform-native store features that crate version
   needs for Windows Credential Manager and macOS Keychain; say which in your report.
2. Write `secrets.rs`. `owner` must match `^(_core|[a-z][a-z0-9-]*)$`, `key` must pass
   `is_ident`; else `Error::Invalid`. `get` maps "no entry" to `Ok(None)`.
3. Memory backend behind `MEMORY_BACKEND_ENV`: a `static` `Mutex<HashMap<String, String>>`.
4. Keychain compatibility check (INTERFACES.md §8.7), on the Windows PC: read
   `scripts/keychain-check.mjs` and how v2 writes credentials (`packages/core/src/` search
   `cross-keychain`/`keychain`). Write one dummy secret the v2 way (run v2's own script or a
   one-off `node -e` with `cross-keychain` from the repo's `node_modules`, using the account
   `_v3check.probe` and the value `not-a-secret`), read it with `secrets::get("_v3check",
   "probe")`, then delete it. Record the result (works / does not, and the exact target name
   each side uses) in your report. Do not commit the one-off script.
5. Write the tests.

## Tests
`tests/secrets.rs` (each test sets `MEMORY_BACKEND_ENV` first):
- `set_get_delete_round_trip`: set, get returns it, delete, get is `None`; deleting again is Ok.
- `owners_are_separate`: `a.key` and `b.key` don't see each other.
- `delete_all_removes_listed_keys_only`.
- `bad_owner_or_key_is_invalid`: owner `A`, `../x`, key `a.b` are `Error::Invalid`.
- `errors_never_contain_the_secret`: force a failure path (an invalid key with the secret value
  as the key is rejected) and assert the error's `Display` doesn't contain the value.

In `src/secrets.rs`, one `#[cfg(windows)]` unit test:
- `windows_credential_manager_round_trip`: with the memory backend **off**, set/get/delete
  `_v3test.probe` = `not-a-secret` in the real Credential Manager. This runs on Windows dev
  machines and the `windows-latest` CI runner (which has Credential Manager).
