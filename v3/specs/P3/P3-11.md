# P3-11: Scheduler: patterns, routine, automation and skill suggestions

Model: opus
Depends on: P3-10
Feature IDs: PR-13, PR-23, PR-24, ME-17

## Goal
Once a week (and the first time after a week of data) the scheduler looks back and notices
things nobody told it: when the owner usually starts and ends the day (their routine), a
question they ask over and over at the same time of week (an automation worth offering), a
multi-step task done the same way several times (a skill worth learning), and notices they
keep dismissing (a mute worth offering). Each finding is a `Low` notice for the weekly review,
phrased as an offer. Nothing changes until the owner says yes in the chat, and the agent then
uses the tools it already has (`schedule.add`, the learned-skills offer, `/mute`).

## Interfaces
```rust
// patterns.rs
/// kv `_core`/`activity`: per local date, the first and last `Active` time (minutes after
/// midnight), the newest 90 days.
pub(crate) fn record_active(store: &Store, at: Ms, tz: &impl TimeZone);
#[derive(Debug, PartialEq)]
pub struct Routine { pub weekday_start: Option<u16>, pub weekday_end: Option<u16>,
                     pub weekend_start: Option<u16>, pub weekend_end: Option<u16> } // minutes; median of ≥ 5 days
pub fn routine(activity: &serde_json::Value) -> Routine;
#[derive(Debug, PartialEq)]
pub enum Finding {
    /// ME-17: the brief's earliest/fallback differ from the routine start by ≥ 45 min.
    Routine { start: u16, end: u16 },
    /// PR-23: ≥ 3 user messages in ≥ 3 different weeks, same weekday, within ±90 min, whose
    /// normalised text (lowercase, words only, stop words out) shares ≥ 60% of words.
    Automation { example: String, weekday: u8, minute: u16 },
    /// PR-24: ≥ 3 finished runs in 30 days with ≥ 5 steps whose first user message normalises
    /// to the same words (≥ 70% shared) and whose tool sequences are equal.
    Skill { example: String, runs: u32 },
    /// PR-13: ≥ 3 notices from one source dismissed (`not_useful` or dropped) in 14 days.
    Dismissed { source: String, count: u32 },
}
pub fn find(store: &Store, now: Ms, tz: &impl TimeZone) -> Vec<Finding>;
```
Each finding becomes a notice: source `"pattern"`, key `pattern:<kind>:<stable hash of the
finding's example or source>`, urgency `Low`, `why` one sentence ("You asked this 4 Mondays in
a row."), and `text` an offer:
- Routine: "You usually start around 07:40 on weekdays. Want the morning brief then?"
- Automation: "You ask “<example, ≤ 80 chars>” most Mondays around 08:00. Want me to do it on my
  own each week?"
- Skill: "You've had me “<example>” 3 times the same way. Want me to learn it as a skill?"
- Dismissed: "You've waved off <n> notes from <source> lately. Shall I stop those?"
The same key is never filed twice while live, and a dropped one is not offered again for 60
days (check `notices_since` for a dropped row with that key).

Private conversations (kv `_core`/`private_sessions`) are left out of every pass. A finding's
example never quotes a private chat.

## Steps
1. Record activity from the bus `Active` events (subscribe in `run`, handle `Lagged`).
2. Write the four detectors as pure functions over plain inputs (activity JSON; `(Ms, text)`
   pairs; `(first message, tool names, steps, at)` from `runs`; notice rows), then `find`
   reads the store and calls them.
3. The weekly pass runs 1 h before `cfg.weekly` (so its notices are in the weekly review), and
   once at start when it has never run and the store has ≥ 7 days of messages.

## Notes for the worker
- 16 GB RAM: `CARGO_BUILD_JOBS=1`; `cargo test -p alexia-scheduler` while working.
- Reading every session's history weekly is fine at one owner's scale (thousands of rows).
  Read only messages newer than 35 days (`history` returns oldest-first per session; stop
  early).
- Why offers, not actions: PR-23/PR-24 are suggestions by the owner's own words, and D214 says
  she acts silently only on what the owner approved. A new schedule is the owner's to accept.
- The run body's shape is in `alexia-core/src/trace.rs`; read tool names from there, not from
  audit rows, which are redacted.
- Invariants: no plugin id in a crate, no user paths, 127.0.0.1 only, examples quoted in notices
  are the owner's own words and never go to a log.
- (CEO #21) If you add a ScheduleTools builtin, you may add its name to the two exact tool lists in tests/scheduler.rs (tools_have_annotations, schedule_tools_do_not_keep_scheduler_alive); nothing else in that file.
