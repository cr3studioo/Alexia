# P3-40: A plugin's capability upcall to memory.* never unlocks locked memory

Model: opus (security: the owner's locked facts)
Depends on: none (found by the P3 phase review, finding 2)
Feature IDs: ME-13 (locked private memory)

## Goal
P3-15/P3-16 promise that locked memory stays locked: only core's own profile and recall reads
may send `unlocked: true`. `agent.rs` `lock_memory` forces `false` on the model's tool calls.
A plugin's `alexia/capability/call` upcall does not. `serve.rs` `AlexiaCall::CapabilityCall`
passes `p.arguments` to `call_capability_as` untouched. So any plugin that declares
`requires: memory.recall` or `memory.profile` can send `unlocked: true` and read the owner's
locked facts. Today that is day-planner, task-list and persona, plus any library plugin. After
this task, every capability upcall whose target capability starts with `memory.` has
`unlocked` set to `false` before it reaches a provider or core. That holds whatever the plugin
sent.

## Interfaces
None change. The rule is in `serve.rs`, keyed by capability and never by plugin id:
```rust
/// The argument only core's own reads may set (P3-15). Same name as core's `UNLOCKED`.
const UNLOCKED: &str = "unlocked";
const MEMORY: &str = "memory.";

/// A plugin's upcall never unlocks memory: `unlocked` is forced to false on every call to a
/// `memory.*` capability, present or not.
fn lock_memory(cap: &str, args: &mut Map<String, Value>);
```
Inside `AlexiaCall::CapabilityCall`, after the `requires` check and before
`call_capability_as`: `let mut args = p.arguments.unwrap_or_default(); lock_memory(&p.cap, &mut args);`.
Setting it always (`args.insert(UNLOCKED, false)`) is deliberate. A missing key is read as
false by the memory plugin today, and an explicit false still holds if a provider's default
ever changes. Other capabilities are untouched, including a non-memory capability that the
memory plugin also provides.

## Steps
1. Read `serve.rs` `AlexiaCall::CapabilityCall` and `host.rs` `call_capability_as`. Both
   branches, the plugin provider and core's own `Upcalls::host_call`, get `args` from that one
   place. Check this, so a single fix covers both.
2. Add `lock_memory` as above and call it in the `CapabilityCall` arm only. `ComputeRun` and
   the other arms stay as they are.
3. Doc comment on the arm: why (P3-15: only core may unlock), and that it is by capability.

## Tests
`tests/upcall_lock.rs`. Follow `alexia_layer.rs`'s setup in the new file (scratch dir,
`plugin(..)` manifests, `host.serve_for_test`). Do not change that file or the fixture. The
provider is a small Node MCP server written by the test, as `alexia-hub/src/proactive.rs`'s tests
do. It provides `memory.recall` and `memory.profile`, appends each call's `arguments` as one JSON
line to a file in its folder, and answers `{"content":[{"type":"text","text":"ok"}]}`. The asker
is the `mcp-fixture` `storage` mode with `requires` listing the caps (as `asker_and_provider`).
Every test below fails on today's code:
- `upcall_unlocked_true_is_forced_false`: the asker sends `alexia/capability/call`
  `{cap: "memory.recall", arguments: {query: "x", unlocked: true}}` → the provider's recorded
  arguments are `{query: "x", unlocked: false}`.
- `upcall_without_unlocked_gets_false`: `{cap: "memory.profile", arguments: {}}` → recorded
  `{unlocked: false}`.
- `upcall_unlocked_string_or_number_is_false`: `unlocked: "true"` and `unlocked: 1` → both
  recorded as `false`.
- `core_answered_memory_cap_is_locked_too`: no plugin provides `memory.recall`. The host's
  `Upcalls` is a test fake whose `host_call` records `args` and answers `Some(Ok(..))`. The
  upcall with `unlocked: true` → the fake saw `unlocked: false`.
- `other_caps_untouched`: a provider of `demo.echo` (same Node server) gets
  `{unlocked: true, a: 1}` exactly as sent.
- `requires_still_checked_first`: an asker without `requires: memory.recall` → -32051, and the
  provider is never started (as `capability_call_needs_requires`).
