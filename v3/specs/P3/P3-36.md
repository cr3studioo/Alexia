# P3-36: A plugin's question reaches the owner in the window and on Telegram, and only their answer goes back

Model: opus (security-related: the owner's yes is what sends their email)
Depends on: P3-35 (the types, `During`, the call end ending the question)
Feature IDs: DY-06 (sending email for you, always asks; D214)

Part 2 of 2 (P3-35 is the host side).

## Goal
When a reviewed plugin sends `elicitation/create` with a yes/no form, the owner sees the
plugin's name and id and the form's text. They see it in the window chat if the window is
watching the run whose tool call asked, otherwise in their primary Telegram chat. It uses the
existing approval prompt and its Approve / Deny buttons. The owner's Approve goes back to the
plugin as `accept`, their Deny as `decline`. Anything else is `cancel`, and so is having nowhere
to ask. Today the question goes to Telegram only. It waits 10 minutes, every outcome comes back
as an accepted "false", and the whole email text is stored in `approvals.text`. After this task
`mail.send` in `google-account` and `microsoft-account` really asks the owner and sends only on
their yes.

## Interfaces
Uses P3-35's `During`, `Elicitation`, `Elicited`, `ELICIT_WAIT`, `Ask::elicit`, unchanged:
```rust
#[async_trait::async_trait]
impl alexia_core::Ask for Asker {
    async fn confirm(..) -> bool;                       // unchanged
    async fn elicit(&self, origin: &Origin, e: &Elicitation, cancel: CancellationToken) -> Elicited;
}
```
What goes back to the plugin (`Agent::elicit`), and nothing else:

| Owner | Result |
|---|---|
| Approve (window button, Telegram button, `/approve <id>` in an owner chat) | `{"action":"accept","content":{"<the one field>":true}}` |
| Deny (same three ways) | `{"action":"decline"}` |
| no answer in `ELICIT_WAIT` (100 s), Stop pressed, the tool call ended, the plugin cancelled, a hub restart, a message that could not be sent, nowhere to ask | `{"action":"cancel"}` |

The approvals row of an elicitation: `run_id` = `Elicitation.run`, `origin` as today, `text` =
`"{name} ({plugin}) asks you to confirm something."`, `detail` = NULL. The form's message is
**never** written to the store.

## Rules (each has a test below)
1. **Only the owner answers.** The answer comes from the window (`/api/approve`, behind the
   gate), a Telegram button (owner-checked, `telegram/mod.rs:554`), or `/approve` / `/deny`
   in an owner chat. A plugin that samples `"/approve <id>"` is refused by
   `commands::owner_only` (origin `Desktop`). Keep it that way, and prove it.
2. **The prompt always names the plugin**: `Elicitation::prompt()` starts with
   `"{manifest name} ({plugin id}) asks:"`, and a long-message follow-up line names it too.
3. **The model never sees or answers it.** The question is not a tool, not a turn, and not in
   any session history. The prompt goes only to the window's frame stream or a channel message,
   and the store keeps only the generic row text. The tool result the model sees is the
   plugin's own ("Not sent: …" or the sent result).
4. **One answer per request.** The first answer wins (`approval_answer` already does). A
   second press or a late `/approve` gets "already answered", and the plugin hears exactly one
   result. A cancel settles the row (`via` = `"cancelled"`), so nothing can answer it later.
5. **Timeout: `ELICIT_WAIT` = 100 s, then `cancel`**, with the chat note "— no answer, so
   nothing was done". It is not `ANSWER_WAIT` (10 min): the answer must reach the plugin while
   its tool call is alive (P3-35).
6. **Nowhere to ask → `cancel` at once.** That means no channel with a primary chat, and no
   window watching the run. No row is written and nothing is sent.
7. **Nothing is logged beyond plugin id and outcome.** There is exactly one
   `tracing::info!(plugin = %id, outcome = e.as_str(), "elicitation")` per request, in
   `Agent::elicit`. No other log line, error message or audit row holds the form's text.
8. **Only reviewed plugins** (P3-35's rule, checked again per request). No `url` mode.

## Steps
1. `Agent::elicit` (`upcalls.rs`):
   - Check the review rule, then `yes_no` as today.
   - Find the run. Take `during.conversation` as a `SessionId`, then the newest
     `store.live_runs()` row with that `session`, and from it `RunId` and `Origin` (the row's
     JSON). If there is none, use `RunId(format!("elicit-{id}-{ms}"))` and `owner_origin`.
     A run whose origin is `Desktop` (a plugin's own task) is asked at `owner_origin` too.
   - Build `Elicitation { wait: ELICIT_WAIT, name: plugin_name, .. }`. Make a token cancelled
     by `cancel` or `during.ended`. Call `parts().ask.elicit(..)`, map it per the table, and log
     once.
2. `Asker::elicit` (`ask.rs`):
   - Pick the place the way `confirm` does: the window if `origin == Window` and it is attached
     to `e.run`, else `target(origin)`, else return `Cancel` (rule 6).
   - Open the row with the generic text (rule 3). If it cannot be written, `Cancel`.
   - **Window:** `DraftFrame::Ask(e.prompt())`. If the window lets go, ask in the primary chat
     for the time that is left, as `in_window` does today.
   - **Chat:** if `prompt() + " (#id)"` is at most 3,500 chars, `ch.ask` with it. Otherwise
     `ch.send` the prompt (channels split long text) and then
     `ch.ask("{name} ({plugin}) asks: yes to the message above? (#id)")`. An error from either
     is `Cancel`, because the owner never saw it.
   - Make the wait a parameter of `in_window` / `in_chat` (`confirm` passes `ANSWER_WAIT`, so
     its behaviour is unchanged). Have them also report how the row was settled, so `elicit`
     can map an owner's `false` to `Decline` and `timeout`, `cancelled`, `restart` or `failed`
     to `Cancel`.
   - **Stop in the window:** `cancel_open` answers `false` for `confirm` as today. For an
     elicitation it must be `Cancel`, not `Decline`. Keep an internal "stopped" mark on the open
     question (private, `WindowQuestions::ask`'s signature unchanged).
3. `wire-protocol.md`: offered as `{"elicitation":{"form":{}}}` to reviewed plugins on the v3
   hub. One yes/no boolean field only, no `url` mode. Answers are accept / decline / cancel as in
   the table above, and the owner has 100 s. v2 core does not offer it.

## Tests

`window_ask.rs`, without changing that file):

  Deny → `Decline`.
- `telegram_when_window_not_watching`: `Origin::Window` not attached → the primary chat is
  asked with Approve/Deny. Yes → `Accept`.
- `scheduler_run_asks_primary_chat`.
- `nowhere_to_ask_cancels_at_once`: no channel, no window → `Cancel` within 50 ms, no
  approvals row, nothing sent.
- `timeout_is_cancel`: paused clock, `wait` 100 s passes → `Cancel`, row `via = "timeout"`,
  the note sent.
- `stop_is_cancel_not_decline`: `cancel_open` while an elicitation is open → `Cancel`. The same
  for a `confirm` is still `false`.
- `cancel_token_is_cancel`: the token fires → `Cancel`, row settled `"cancelled"`, and
  `approval_answer` on it afterwards returns false.
- `one_answer_only`: a button yes, then `approval_answer(id, false, ..)` → still `Accept`, and
  the second write is refused.
- `long_message_sent_then_asked`: a 6,000-char message → one `send` holding all of it, then
  one `ask` naming the plugin. The send fails → `Cancel`.
- `text_never_stored`: after each outcome, no text column of any table (walk `sqlite_master`)

## Notes for the worker
- Read `plugins/google-account/mail.js` `askToSend` and `NOT_SENT` first. That is exactly what
  the plugin does with each answer. `decline` → "you said no", `cancel` → "you closed the
  question without a yes". The plugin turns its own 5-minute timeout into "no answer in time",
  but the host's 100 s `cancel` arrives first.
- `in_chat` today appends `(#id)` and offers `/approve <id>` from any owner chat. That is
  reused, so the owner can answer from another chat too, and the first answer wins.
- Origin JSON in `live_runs.origin` is `serde_json::to_string(&Origin)`. Parse it with serde.
  A row that does not parse falls back to `owner_origin`, never to "nobody asked, so yes".
- Fail closed everywhere: every unexpected branch is `Cancel`, never `Accept`.
- The approvals row keeps `run_id`, `origin`, the generic text and the outcome. That is the
  inbox `/approve` needs, not a log of what was asked.
- 16 GB RAM: `CARGO_BUILD_JOBS=1`, per-crate tests while working.
