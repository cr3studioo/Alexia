# P3-05: McpHost: call every provider of a capability

Model: opus
Depends on: P3-02
Feature IDs: PR-01

## Goal
The host can ask every enabled plugin that provides a capability, at once, and collect their
answers. The proactivity engine needs this: "what might be worth saying" (`notice.items`) and
"a section for the brief" (`brief.section`) are offered by many plugins, and the engine must
reach all of them without naming any. Today `call_capability` picks one provider.

## Touch only these paths
- `v3/crates/alexia-mcp/src/host.rs`   (change: add `call_capability_all`)
- `v3/crates/alexia-mcp/src/bin/mcp-fixture.rs`   (change: an option to provide a capability with a configurable answer and delay)
- `v3/crates/alexia-mcp/tests/fanout.rs`   (create)

## Must not touch
`call_capability`'s behaviour, the supervisor, `alexia-mcp/tests/supervise.rs` (it has a known
flake, P2D L7), other crates.

## Interfaces
```rust
impl McpHost {
    /// Every enabled provider of `cap` that is not held (P2-62), in §2.2's resolution order
    /// (lowest `installed_at`, else id), called concurrently with `ctx` cloned per call, each
    /// with its own `per_call` timeout. Errors, `isError` results and timeouts are left out and
    /// logged at warn with the plugin id. The results carry nothing naming the plugin.
    /// No provider → empty Vec. Spawns lazily like `call_tool`.
    pub async fn call_capability_all(
        &self,
        cap: &str,
        args: serde_json::Map<String, serde_json::Value>,
        ctx: CallCtx,
        per_call: std::time::Duration,
    ) -> Vec<types::CallToolResult>;
}
```
Fixture: `mcp-fixture` accepts (environment or args, as its existing options do)
`FIXTURE_PROVIDES=<cap>`, `FIXTURE_ANSWER=<text>`, `FIXTURE_DELAY_MS=<n>`, `FIXTURE_FAIL=1`, so
tests can install three providers of one cap from one binary under three plugin ids.

## Steps
1. Find the providers the way `call_capability` does (tools whose `provides` lists `cap`),
   but keep all of them, one call per plugin (the first matching tool of each plugin).
2. Call them with `futures`-free concurrency (`tokio::task::JoinSet` or `join_all` written
   with `JoinSet`), each wrapped in `tokio::time::timeout(per_call, ..)`.
3. Order the output in resolution order, not completion order.

## Tests
`tests/fanout.rs` (three fixture plugins under scratch ids, built as the other mcp tests do):
- `all_providers_answer_in_order`: three providers → three results in install order.
- `failing_and_slow_are_left_out`: one fails, one sleeps past `per_call` → one result, and the
  call returns within `per_call` + 1 s.
- `no_provider_is_empty`.
- `held_provider_is_skipped`: `hold` one → two results.
- `disabled_provider_is_skipped`.

## Notes for the worker
- 16 GB RAM: `CARGO_BUILD_JOBS=1`; `cargo test -p alexia-mcp --test fanout` while working.
  `alexia-mcp/tests/supervise.rs` can hang under load (P2D L7). If it does in the final
  workspace run, run it alone and record that in your report.
- Why fan-out (PHASE.md D-P3-2): the scheduler must never name a plugin (rule 1), yet it needs
  every source. Capabilities are the only coupling (rule 2).
- Windows: the fixture's children are in a Job Object like any plugin. Kill nothing yourself.
- Invariants: no plugin id in crate code (tests use scratch ids), no user paths, 127.0.0.1 only,
  no secrets in logs (log only the plugin id and the error kind).
