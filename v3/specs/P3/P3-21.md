# P3-21: Microsoft 365: calendar, mail reading, contacts

Model: opus
Depends on: P3-03
Feature IDs: DY-02, DY-17 (contacts)

## Goal
The `microsoft-account` plugin connects an Outlook or Microsoft 365 account (personal or
school) with the device-code flow, and provides the same capabilities as the Google plugin
from Microsoft Graph: calendar (read, create asks first), mail reading (never marking read)
and contacts. Code on top uses the capabilities and does not care which account answers.

## Touch only these paths
- `plugins/microsoft-account/**`   (fill: `index.js`, `oauth.js`, `calendar.js`, `mail.js`, `contacts.js`, `plugin.json`, `README.md`, `test/*.test.js`)

## Must not touch
`package.json` (no new dependency), the Google plugin (shared ideas, no shared code: plugins do
not depend on plugins), other plugins, crates.

## Interfaces
- `requires`: `net.request` ("to talk to Microsoft: login.microsoftonline.com,
  graph.microsoft.com").
- Settings: `client_id` (text: the owner's app registration, public client),
  `tenant` (text, default `common`), `refresh_token` (password, hidden), `connect` (action:
  shows the device code and URL in the status and the chat), `status`.
- Device code flow: `POST /{tenant}/oauth2/v2.0/devicecode` with scopes `offline_access
  Calendars.ReadWrite Mail.Read Contacts.Read User.Read` (P3-24 adds `Mail.Send`), poll the
  token endpoint at the given interval until done or expired. The user code is shown; the
  device code and tokens are never shown or logged.
- Capability tools and `notice_items`: as P3-20 (same shapes, keys `microsoft:event:<id>`),
  with Graph's `calendarView`, `messages` (`$select`, never `PATCH`), `contacts`.
- When the tenant refuses consent (AADSTS65001 and similar), the status says: "Your
  organisation does not allow Alexia to connect. Ask its IT, or use a personal account." That
  is the DY-02 limit in PHASE.md *Owner needs* 4.

## Steps
As P3-20: `oauth.js` (device code, refresh) tested with a fake endpoint; mappers pure and
tested on hand-written Graph-shaped JSON; tools; README with the app registration steps.

## Tests
`oauth.test.js`: `device_code_polls_until_done`, `expired_code_says_so`,
`consent_refused_sentence`, `tokens_never_in_output`. `calendar.test.js`, `mail.test.js`,
`contacts.test.js`: shapes match INTERFACES §3.6, mail list never PATCHes, create is
open-world.

## Notes for the worker
- No Rust. Cargo checks, if run: `CARGO_BUILD_JOBS=1`.
- Both account plugins may be enabled at once; the scheduler fans `notice.items` out to both,
  and `calendar.events` resolves to the one installed first. Say that in the README.
- Invariants: no plugin names, no user paths, secrets only in `password` settings, no mail or
  event text in logs.
