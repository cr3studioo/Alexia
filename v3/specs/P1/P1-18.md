# P1-18: End-to-end latency test and the 50-message run

Model: sonnet
Depends on: P1-17, P1-26
Feature IDs: CH-03, SP-03, SP-09 (the done-when, measured)

## Goal
After this task V3-1's done-when is proved by a test, not claimed. `tests/telegram_e2e.rs` runs
the real `alexia-hub run` binary against a fake Bot API, fake free providers and a fake v2 core,
sends 50 messages, and asserts the reaction lands within 300 ms of receipt every time, that no
chat-lane message ever reaches v2, and that every turn's spans account for its time. Then the
same check runs on the PC on 50 real messages, and the result is written up.

## Touch only these paths
- `v3/crates/alexia-hub/tests/telegram_e2e.rs`   (create)
- `v3/ops/reports/P1-latency.md`   (create: the by-hand run's numbers and the dashboard summary)

## Must not touch
Any `src/` file in any crate. If the test finds a bug, stop and report it with the failing
assertion; the fix is a follow-up task.

## Interfaces
The test hooks the earlier tasks provide:
- `ALEXIA_TELEGRAM_API` (P1-09): the fake Bot API's base URL.
- `ALEXIA_FREE_PROVIDERS` (P1-04): a JSON file listing two fake providers (keyless, `all_free`).
- `ALEXIA_V2_URL` + `ALEXIA_V2_TOKEN` (P1-13): the fake v2 core; no child is spawned.
- The bot token comes from the environment fallback P1-03 adds to `secrets::get`
  (`secrets::env_name("_core", <the key from alexia-hub secret list>)`), set to a dummy value;
  `ALEXIA_SECRETS_IN_MEMORY=1` keeps the real keychain out of the test.
- `ALEXIA_HUB_STOP_ON_EOF=1` (P0-14).
- `alexia-hub latency --last 50 --check` (P1-15), run against the same data dir afterwards.

## Steps
1. In-test servers (tokio `TcpListener`, raw HTTP/1.1, one helper module inside the test file):
   - **Bot API**: `getUpdates` hands out a scripted queue of updates (first a pairing message
     with the code read from the hub's stdout, then the 50 messages, 300–900 ms apart);
     `setMessageReaction` records `Instant::now()` per message id; `sendMessageDraft` and
     `sendMessage` are recorded; everything else answers `{ok:true,result:true}`. The receipt
     moment is the instant the fake **finished writing** the `getUpdates` response that carried
     the message.
   - **Two free providers**: OpenAI-compatible `/models` and `/chat/completions` SSE; provider A
     answers in 200–600 ms, provider B in 400–1200 ms (seeded random), so hedging is exercised.
   - **v2 core**: `GET /` returns a page containing a UUID, `/api/chat` counts requests and
     streams three `delta` events after 5 s (a slow task), `/api/stop` and `/api/approve` answer
     `{}`.
2. The 50 messages: 30 chat ("hi", "thanks", "how's it going", …), 20 tasks ("remind me…",
   "search…", "https://…"). Two pairs are sent 200 ms apart (merge), one task gets a follow-up
   after its first draft (steer).
3. Assert:
   - every message got a reaction, and reaction − receipt < 300 ms for all 50 (print p50/p95/max);
   - the fake v2 received exactly the task messages (20, plus the steer follow-up, minus merged
     ones) and **none** of the 30 chat messages;
   - every chat message got a reply through `sendMessage`;
   - after `run` stops, `alexia-hub latency --last 48 --check` exits 0 (48 = 50 minus the two
     merges) and `--html` writes a file.
4. Run it 5 times in a row; it must pass every time (timings use real time, so give the 300 ms
   assertion no slack beyond what the spec says).
5. **By hand on the PC** (reported in `v3/ops/reports/P1-latency.md`, never with message text,
   chat ids or keys): with the real bot and keys set up per PHASE.md *Owner needs*, the owner
   uses Telegram for 50 messages; then run `alexia-hub latency --last 50 --check --html
   latency.html`. Record: the check's exit code and lines, the per-stage summary table it
   printed, ack p50/p95/max, chat vs task counts, median receipt → first draft and receipt →
   delivered per lane. Attach `latency.html` to the report only if it contains no message text
   (it shouldn't; check).

## Notes for the worker
- What this measures: hub receipt → Telegram's answer to `setMessageReaction`. The phone's
  view adds Telegram's own delivery both ways, which the Bot API can't time (`date` has
  one-second resolution). Say that in the report rather than claiming a phone-side number.
- CI runners are slower than the PC; if the 300 ms assertion fails only on CI, report the
  measured numbers — don't widen the threshold.
- Never put the real bot token or provider keys in the test, the report or a log.
