# P1-29: Telegram: finish only what was delivered; pairing closes once paired

Model: opus
Depends on: P1-28
Feature IDs: CH-01

## Goal
Two fixes in the Telegram adapter, both in `channels/telegram/mod.rs`.

**A reply that never arrived is replayed after a restart.** `draft(None)` (`:660-665`) marks
every started update of the chat finished, so a stopped turn is not replayed (v2 `Acks`). But
the gateway also calls `draft(None)` after every delivery, including a failed one
(`gateway.rs` `deliver`, `:885`: `send` fails, the error is logged, then `draft(None)`), and
after a failed "keep the draft" send on a steer (`:483-487`). So today a reply whose `send`
failed is marked done, and a restart does not replay the message. After this task the
adapter finishes a chat's updates only on a successful `send` or on a `draft(None)` that did
not follow a failed `send` in that chat (a stopped turn). The fix stays in the adapter: the
gateway's calls are right (the draft must be cleared either way), and `gateway.rs` belongs to
P1-26.

**A stranger cannot keep the owner from pairing.** `stranger` (`:403-411`) counts wrong
guesses in one counter for everyone, and still compares and rotates after an owner is paired.
So any account that finds the bot can send five wrong codes, over and over, and the code the
owner was shown is gone each time (a denial of service on pairing). P1-10 shows the code only
while nobody is paired (`tell_if_unpaired`, `channels::pairing_codes` "with no owner yet"), so
once an owner exists no one can know the code and accepting it serves nobody. After this task:
- once `telegram_owners` is non-empty, a stranger's message is dropped with no code compare,
  no count and no rotation (P1-10 step 2's "no reply" still holds);
- while unpaired, misses are counted **per sender id**; the code rotates when one sender
  reaches five, and only that sender's count resets.

## Interfaces
Unchanged. `Channel` keeps its signatures; `Telegram::new` and `pairing_code` are unchanged.
Private fields change:

```rust
// in `struct Telegram`
misses: Mutex<HashMap<i64, u32>>,   // was `misses: AtomicU32`; sender id → wrong guesses
failed: Mutex<HashSet<i64>>,        // chats whose last `send` failed
```

## Steps
1. **send**: on any error (a chunk, a document or the voice note; also "nothing to send"),
   insert the chat into `failed` before returning the error; nothing is finished. On success,
   remove the chat from `failed`, then `finished(chat)` as today.
2. **draft(None)**: remove the draft id as today; then `if !lock(&self.failed).remove(&chat)
   { self.finished(chat) }`. Update the comment: a cleared draft with nothing sent is a stopped
   turn and is done; one that follows a failed send is not, so a restart replays it.
3. **stranger**: first `if !owners(&self.store)?.is_empty() { return Ok(()) }` (before
   `pairing_code()`, so a paired bot never creates a code). Then per-sender misses: on a wrong
   guess, bump `misses[user]`; at `GUESSES`, remove that entry, rotate and log as today. A right
   guess clears the whole map. Replace the `ponytail:` comment: the map lives in memory, so a
   restart grants five more guesses per sender, and many accounts can still rotate the code
   before pairing; the owner is at the console then and sees the new code in the log.
4. Remove the `AtomicU32` import if nothing else uses it.

## Notes for the worker
- Rebase on the merged P1-28 first (it changes `fn base64` in the same file).
- Security: `from_owner` and pairing are the trust boundary (P1-10's notes). Nothing here may
  let a stranger in: a paired bot must never add an owner, whatever the text.
- A failed send's updates stay open until the next successful `send` in that chat, which
  finishes every started update of the chat (P1-10 step 3). So the message is replayed only by
  a restart before that; that is the v2 rule, keep it.
- A send that fails partway through a split reply leaves the first chunks delivered; a replay
  sends them again. Accepted: a duplicate beats a lost reply.
- Pairing a second account after the first is not supported by P1-10's code surfacing either
  (no command shows the code once paired); if the owner needs it, that is its own task.
