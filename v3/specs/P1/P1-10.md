# P1-10: Telegram channel: poll, pairing, offsets, buttons

Model: opus
Depends on: P1-09, P1-03
Feature IDs: CH-01, CH-03, CH-05, CH-06, CH-07, CH-08

## Goal
After this task the hub has a `Channel` for Telegram: it long-polls from the PC, turns updates
into `Inbound`s stamped with the moment the hub received them, knows which accounts are the
owner's (pairing by a one-time code, a port of v2's), never answers twice after a crash (v2's
offset rule), downloads photos and voice notes, turns the draft's Stop button into
`InKind::Stop`, and resolves `ask()` from the owner's button press. `channels::configured`
returns it whenever the bot token is in Credential Manager.

## Steps
1. **Receipt time**: `Inbound.at` = `now_ms()` taken immediately after `get_updates` returns,
   one value for the whole batch. This is the start of the 300 ms the done-when measures.
2. **Owners and pairing** (port `plugins/telegram/index.js` pairing, around `allowed` /
   `pairing_code`): a private-chat message from a user id in `telegram_owners` →
   `from_owner: true`. Any other message whose trimmed text equals the code → add the user,
   rotate the code, `set_primary_chat("telegram", chat)`, reply "Paired. I'm listening."; it is
   not passed on. Anything else from a non-owner: not passed on, no reply (a bot found by
   accident says nothing). Group chats are ignored in P1. While unpaired, `next()` logs
   `"Waiting to be paired — send <code> to the bot"` once per start at info (the code is not a
   secret worth hiding from the owner's own console, but never goes to the bus).
3. **Offsets** (port `plugins/telegram/acks.js` `Acks`): the saved offset is the oldest update
   not yet finished, else one past the newest. `next()` marks updates started; the gateway's
   delivery marks them finished through a crate-private `Telegram::finished(msg)` called from
   `send` of the final reply (`send` with `Outbound` for that chat finishes every started update
   of that chat). Restart reads `telegram_offset`.
4. **Content**: text or caption → `Content::Text`. Photo: the largest size under 10 MB
   (v2 `bestPhoto` in `incoming.js`) downloaded to `cache/telegram/<update_id>.jpg`, then
   `Content::Parts([Text(caption), Image { url: data:image/jpeg;base64,… }])`. Voice/audio:
   downloaded to `cache/telegram/<update_id>.ogg` → `InFile { mime: "audio/ogg" }`, content =
   caption or empty text. Documents: `InFile` with the document's name and mime, content =
   caption. Files are deleted by the gateway after the turn (P1-11).
5. **Stop**: `stopped_message_generation` → `Inbound { kind: Stop, .. }` for that chat.
6. **ask()**: `send_message` with buttons `[("Approve","y:<n>"),("Deny","n:<n>")]`, register
   `<n>` in a map of `oneshot::Sender<bool>`; the poll loop routes `callback_query` with that
   data from an owner to it (answer_callback, remove_buttons, edit the text to add "— approved"
   or "— denied"). Cancel → remove buttons, `Ok(None)`. A press from a non-owner is answered
   with "Only the owner can answer this." and ignored.
7. **draft()**: one `draft_id` per chat per reply (v2 `draftId()`), `can_stop: true`;
   `None` sends nothing (Telegram drops an unrefreshed draft by itself after ~30 s) and forgets
   the id. Text over 4096 characters is cut to the last 4096 (the draft shows the tail).
8. **send()**: split text at 4096 on paragraph, then line, then word boundaries (v2
   `chunk()` in `api.js`); files go as documents; `voice: true` with one `audio/ogg` file goes
   as a voice note. Returns the last message's id.
9. **Errors from the poll**: `Conflict` → log "Another program is reading this bot's messages"
   once, back off 10 s doubling to 5 min (v2 `clash.js`); `Unauthorized` → stop polling, log
   "The bot token was refused." and return `Error::Unauthorized` from `next()`; `Unreachable` →
   back off 1 s doubling to 30 s.

## Notes for the worker
- Security: `from_owner` is the trust boundary for everything after it (approvals, tasks that
  act on the PC). Only a user id paired by code is an owner. Never trust `chat.id` alone, never
  a username.
- v2's pairing lives in the v2 plugin's own storage namespace; reading it would make core depend
  on a plugin. The owner pairs once again (PHASE.md *Owner needs*).
- INTERFACES.md §8.1: this adapter must never detect, name or disable v2's Telegram plugin; a
  409 is reported, nothing more.

- From the P1-09 review: an HTTP 5xx with no JSON body maps to TgError::Service, not Unreachable (api.rs ~:175). Treat Service from getUpdates as retryable with backoff, so a Telegram outage does not stop polling.
