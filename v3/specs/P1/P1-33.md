# P1-33: The 50-real-message latency run

Model: sonnet
Depends on: P1-18
Feature IDs: CH-03, SP-03, SP-09 (the done-when, on real messages)

## Goal
V3-1's done-when says the dashboard shows where every second goes **on 50 real messages**.
P1-18 proves it against fakes; this task is the by-hand run on the PC with the real Telegram bot
and real free providers, and the write-up in `v3/ops/reports/P1-latency.md`. No code changes.

## Touch only these paths
- `v3/ops/reports/P1-latency.md`   (create: the by-hand run's numbers and the dashboard summary)

## Must not touch
Any code, test or spec. If the run finds a bug, stop and report it with the failing check line;
the fix is a follow-up task.

## Interfaces
None. Uses `alexia-hub run`, `alexia-hub secret set`, `alexia-hub pair` and
`alexia-hub latency --last 50 --check --html latency.html` (P1-15, P1-17) as built.

## Steps
1. **Needs the owner first (owner ask A-09).** Do not start until the owner has given, on the PC:
   - a test bot from @BotFather (safer than the real Alexia bot before cutover), entered with
     `alexia-hub secret set telegram_bot_token`;
   - keys for at least two free providers (Groq, Cerebras, Google AI Studio, OpenRouter,
     Mistral, NVIDIA, GitHub Models), entered with `alexia-hub secret set provider_<id>`, so
     hedging races something;
   - their OK to race two providers per chat message (each provider's free-tier terms, PHASE.md
     *Owner needs*).
   Everything else is PHASE.md *Owner needs*: only one program reads the bot (v2's Telegram
   plugin off), pairing once, v2 core for the bridge (`ALEXIA_V2_ROOT`,
   `%LOCALAPPDATA%\AlexiaBridge`), outbound HTTPS. If any is missing, report `failed` naming it;
   never set one up on the owner's behalf.
2. The owner pairs (`alexia-hub run` or `alexia-hub pair` prints the code) and uses Telegram
   normally for 50 messages, a mix of chat and tasks, over a day or two.
3. On the PC run `alexia-hub latency --last 50 --check --html latency.html`.
4. Write `v3/ops/reports/P1-latency.md`, **never with message text, chat ids or keys**. Record:
   the check's exit code and lines, the per-stage summary table it printed, ack p50/p95/max,
   chat vs task counts, median receipt → first draft and receipt → delivered per lane, and the
   date and commit the hub was built from. Attach `latency.html` to the report only if it
   contains no message text (it shouldn't; check).

## Tests
None new. P1-18's `telegram_e2e` is the automated proof; this task is the measured one.

## Done when
- `v3/ops/reports/P1-latency.md` exists with the by-hand numbers, and the by-hand
  `alexia-hub latency --last 50 --check` exited 0 (if it didn't, the report says which check
  failed and the task is `failed`, not `succeeded`)
- `git diff --stat` touches only the report (and `latency.html` beside it, if attached)

## Notes for the worker
- What this measures: hub receipt → Telegram's answer to `setMessageReaction`. The phone's
  view adds Telegram's own delivery both ways, which the Bot API can't time (`date` has
  one-second resolution). Say that in the report rather than claiming a phone-side number.
- Never put the real bot token or provider keys in the report or a log.
- After the run, the owner can switch the hub back to the real bot (same `secret set`); that is
  their call, not this task's.
