# P1-09: Telegram Bot API client

Model: opus
Depends on: P1-02
Feature IDs: CH-01, CH-03, CH-04, CH-05, CH-06, CH-07

## Goal
After this task the gateway has a small typed client for the Bot API methods V3-1 uses, ported
from v2's `plugins/telegram/api.js`: long polling (CH-01, nothing exposed), reactions (CH-03),
drafts (CH-04), voice and photo upload and download (CH-05, CH-06), inline buttons and callback
answers (CH-07), with Telegram's errors mapped to `alexia_gateway::Error` (409 Conflict, 429 with
`retry_after`, 401). One kept-alive HTTPS client, so a reaction is one round trip on a warm
connection.

## Touch only these paths
- `v3/crates/alexia-gateway/src/channels/telegram/api.rs`   (fill the stub)
- `v3/crates/alexia-gateway/tests/telegram_api.rs`   (create)

Text over 4096 characters is split by `send_message`'s caller (P1-10), not here; `send_message`
returns `Error::Service` for a 400 "message is too long" so the caller can tell.

## Steps
1. Port `call()` from `plugins/telegram/api.js`: POST JSON to `{base}/bot{token}/{method}`,
   parse `{ok, result, description, error_code, parameters.retry_after}`. Map: 409 →
   `Conflict`; 429 → `RateLimited { retry_after_ms }`; 401/404-on-getMe → `Unauthorized`;
   network → `Unreachable`; other `ok:false` → `Service(<description>)`.
2. Check v2's `api.js` for the exact `sendMessageDraft` / `setMessageReaction` /
   `stopped_message_generation` shapes (Bot API 9.x drafts) and copy them.
3. Uploads (`sendVoice`, `sendDocument`) use reqwest `multipart` (enabled in P1-01).
4. One `reqwest::Client` with `pool_idle_timeout(None)`, `tcp_keepalive(30 s)`, request timeout
   `timeout_s + 10` for `getUpdates`, 15 s for everything else. `get_updates` honours `cancel`
   by `select!` and dropping the request.
5. Redaction: the token is in every URL. Never log a URL; `Api` has a manual `Debug` that prints
   `Api { base }`. reqwest errors carry the URL: map them to `Unreachable` without formatting
   them (`err.without_url()` before any `Display`).

## Tests
`tests/telegram_api.rs`, against a fake Bot API on `127.0.0.1:0` (tokio `TcpListener`, raw
HTTP/1.1, the same small helper style as P1-04's tests; copy it, don't share it across crates):
- `get_updates_parses_text_photo_voice_callback_and_stop`: one canned JSON array covering all
  five kinds (shapes copied from Telegram's docs and v2's `plugins/telegram/test/` fixtures).
- `reaction_body_shape`: the fake records `{chat_id, message_id, reaction:[{type:"emoji",emoji:"👀"}]}`.
- `draft_body_shape`.
- `buttons_body_shape`: `reply_markup.inline_keyboard` with two buttons.
- `status_409_is_conflict`, `status_429_is_rate_limited_with_ms`, `status_401_is_unauthorized`.
- `voice_upload_is_multipart`.
- `download_writes_file_and_refuses_over_20mb`.
- `token_never_in_errors`: force a connect error; `format!("{err} {err:?}")` doesn't contain the
  token.
- `cancel_ends_long_poll`: the fake holds the poll; cancel → returns `Cancelled` within 100 ms.

## Notes for the worker
- The `🗨️` and other emoji: Telegram accepts only its listed reaction emoji; 👀 is on the list.
- Telegram's `date` is in seconds; the gateway times receipt itself (P1-10), never from `date`.
- A bot can't react in a chat where reactions are off; that's a `Service` error the caller
  ignores (the draft still shows something).
