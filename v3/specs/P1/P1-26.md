# P1-26: Documents reach the task lane; no empty assistant turns; bounded prompt fetches

Model: opus
Depends on: P1-07, P1-17, P1-23
Feature IDs: CH-06, SP-03, SP-04

## Goal
Three gaps on the way from a Telegram message to an answer.

1. **Documents never reach v2.** `Inbound.files` carries the documents the Telegram channel
   downloads (P1-10 step 4), but `Turn` (`alexia-core/src/brain.rs:12`) has no files, so the
   gateway (`gateway.rs:776`) drops them and `V2Bridge` (`bridge.rs:550`, `uploads`) sends only
   the image parts of `content`. P1-13's spec already asked for "`InFile`s read from disk
   (documents ≤ 20 MB)"; it could not, for want of the field. After this task a document goes to
   v2 `/api/chat` as an `Upload { name, data, type }`, exactly as v2's own window sends it
   (`packages/core/src/attach.ts`, `serve.ts` `documents()`), and v2 reads it with
   `document.extract` as it always has. A turn with a document always takes the task lane: the
   chat lane cannot read one.
2. **A hung memory plugin stalls the first chat turn.** `FastChat::prefix` (`chat.rs:128`)
   awaits `memory.profile` and `persona.personality` with no bound, one after the other. Recall
   is bounded at 250 ms (SP-04); these two get the same bound, together.
3. **Empty assistant turns are stored.** A model that streams reasoning and no text makes
   FastChat store an empty assistant row (`chat.rs:261`) and return an empty reply (its relay
   flushes nothing, `chat.rs:323`); the bridge stores whatever v2 wrote, empty after a denied
   approval, and the hub's own `FREE_ONLY` sentence as v2's answer after a refused cost ask
   (`bridge.rs:510-516`). An empty row is history noise every later prompt carries, and an
   empty reply is a Telegram message the Bot API refuses.

**Order against P1-17:** this does not need to land before P1-17. P1-17 builds no `Turn`
and reads no file; the wiring is the same with or without the field. It comes after P1-17
because it may add `base64` to `alexia-hub/Cargo.toml`, which P1-17 owns, and it must land
**before P1-18's 50 real messages**, or every document sent in that run is silently dropped.

## Interfaces
`alexia_core` (INTERFACES.md §2.3):

```rust
/// (V3-1) A file that came with a message, already downloaded under `layout.cache()`.
#[derive(Clone, Debug)]
pub struct InFile { pub name: String, pub mime: String, pub path: PathBuf }

pub struct Turn {
    pub session: SessionId,
    pub origin: Origin,
    pub content: Content,
    /// (V3-1) Documents and other files that came with the message, not voice notes (those
    /// are already text in `content`) and not photos (image parts of `content`).
    pub files: Vec<InFile>,
    pub received_at: Ms,
}
```

`alexia_gateway::InFile` becomes `pub use alexia_core::InFile;` in `channel.rs` (same fields
and derives, so every gateway and hub use compiles unchanged); INTERFACES.md §2.4 says so
instead of defining it.

v2 `/api/chat` body, unchanged: `{ "text", "files": [{ "name", "data" (base64, no prefix),
"type" }] }`; v2 takes at most 8 files, 25 MB each, 40 MB together, and says itself which it
refused (`attach.ts` `receive`).

## Steps
1. `brain.rs`: add `InFile` and `Turn.files` as above. Fix every `Turn { .. }` literal:
   `gateway.rs:776`, `bridge.rs` tests (`turn()`), `tests/chat.rs` (`say`), `tests/types.rs`.
2. `channel.rs`: delete the `InFile` struct, `pub use alexia_core::InFile;`.
3. `gateway.rs` (building the turn, ~`:776`): `files` = the merged `inbound.files` whose mime
   does not start with `audio/` (voice notes became text in `voice::hear`). The gateway still
   deletes the files after the turn (`delete_files`); the brain reads them during `reply`.
4. `lane.rs`: a turn with non-empty `files` is `Lane::Task`, checked first, next to the rule
   that sends image parts to the task lane (CH-06). The chat lane never sees a file.
5. `bridge.rs` `uploads`: take the `Turn`; image parts as today, then each `turn.files` entry
   read from disk → `{ "name": f.name, "data": <standard base64>, "type": f.mime }`. Skip with a
   `tracing::warn!` (name and size, never the bytes) a file that cannot be read or is over
   20 MB (Telegram's own download ceiling; past it the JSON body would be the problem). Base64:
   the `base64` crate's `STANDARD` engine (if P1-17 already added `base64` to the hub, use that;
   otherwise add `base64 = "0.22"`, which is in `Cargo.lock` already as 0.22.1). Read with
   `tokio::fs::read`, so a large file does not block a runtime thread.
6. `bridge.rs` `reply` / `save`: let `wrote = !st.text.trim().is_empty()`, taken **before**
   `FREE_ONLY` is appended. The user row is stored as today. The assistant row is stored only
   when `wrote` (its text as today, `FREE_ONLY` included). When `!wrote && !st.refused_paid`,
   return `Err(BrainError::Unavailable(NO_REPLY))` with
   `const NO_REPLY: &str = "The task ended without a reply.";` after storing the user row (v2
   saw it). A refused cost ask with no words still replies `FREE_ONLY`, unstored.
7. `chat.rs` `prefix`: fetch profile and personality together, bounded:
   `tokio::time::timeout(Duration::from_millis(Self::RECALL_WAIT_MS), async { tokio::join!(
   self.cap_text(PROFILE, &child), self.cap_text(PERSONALITY, &child)) })`, where `child =
   cancel.child_token()`; on timeout `child.cancel()` and use `(None, None)`. The prefix built
   without them is cached as usual (it stays byte-identical, SP-05; `invalidate` every 10
   minutes retries), so a hung plugin costs 250 ms once, not every turn. A `ponytail:` comment
   says so.
8. `chat.rs` `reply`: if `text.trim().is_empty()` after `relay`, store nothing, send no
   capture, and return `Err(BrainError::Unavailable(NO_ANSWER))` with
   `const NO_ANSWER: &str = "The free model sent back no answer. Try again.";`. `relay`'s
   final `flush` is skipped when the held text is blank, so no `Writing` phase is drafted for
   nothing.
9. INTERFACES.md §2.3 and §2.4 as above.

## Tests
`alexia-core/tests/chat.rs`:
- `hung_profile_does_not_stall_the_first_turn`: `FakeCaps` with `memory.profile` and
  `persona.personality` at 60 000 ms. The first reply arrives, the provider saw the request
  less than 2 s after the turn started (generous for a loaded machine; the bound is 250 ms),
  and the system prompt has no "What you know about the user". A second turn reuses the same
  prefix (byte-identical system up to the day line) without calling the caps again.
- `reasoning_only_reply_stores_nothing`: `Answer::Chunks([Reasoning("hmm")])` →
  `Err(BrainError::Unavailable(s))` with `s` the `NO_ANSWER` text, `history` empty, no
  `memory.capture` call, no `Delta` frame.
- The existing tests pass (`say` builds the turn with `files: Vec::new()`).

`alexia-core/tests/lane.rs`:
- `file_is_task`: "hi" with one `InFile { mime: "application/pdf" }` → task lane.

`alexia-gateway/tests/gateway.rs`:
- `documents_reach_the_brain_voice_does_not`: an inbound with a `application/pdf` file and an
  `audio/ogg` file → the `FakeBrain`'s recorded turn has exactly the PDF in `files`.

`alexia-hub/src/bridge.rs` tests:
- `documents_go_as_uploads`: a temp file `notes.txt` containing `hello` as
  `InFile { name: "notes.txt", mime: "text/plain", .. }` beside one image part → `/api/chat`'s
  `files` is the image upload then `{ "name": "notes.txt", "data": "aGVsbG8=", "type":
  "text/plain" }`.
- `missing_document_is_skipped`: an `InFile` whose path does not exist → `files` is `[]`, the
  reply still arrives.
- `no_words_store_no_assistant_row`: script `ask` → `Wait("/api/approve")` and nothing else,
  no asker → `Err(Unavailable(NO_REPLY))`, history holds the user row only.
- `paid_is_always_refused` gains: with a script that writes no delta before `paid`, the reply
  is `FREE_ONLY` and history holds the user row only.
- `images_go_as_uploads` and every other bridge test pass.

## Notes for the worker
- Rebase on the merged P1-07, P1-17 and P1-23 first. P1-25 also edits `gateway.rs` (`now_ms`
  only); if it is running, the second of the two to merge rebases.
- Why `InFile` moves to core rather than `Turn` holding `OutFile`s: same shape, but the name
  would lie, and core cannot depend on the gateway (the gateway depends on core).
- The stored user row keeps `turn.content` only; document names are not added to it. v2 keeps
  the extracted text in its own session, and V3-2 owns attachments in v3 history.
- Do not run OCR or extraction in the hub: v2 decides how to read a file (`serve.ts`
  `documents()`), and a picture still goes as a picture.
- Telegram bot downloads stop at 20 MB, so the size skip is a guard, not a path tests need
  real 20 MB files for; test it, if at all, with a sparse file or not at all.
