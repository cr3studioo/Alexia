# P1-21: Telegram api: file transfers and retry_after

Model: sonnet
Depends on: none
Feature IDs: CH-05, CH-06

## Goal
Voice notes, photos and documents survive a slow link. Today `download`
(`v3/crates/alexia-gateway/src/channels/telegram/api.rs:351`) and `upload` (`api.rs:290`, used by
`send_voice` and `send_document`) use `CALL_TIMEOUT` (15 s), and reqwest's timeout covers the
whole body, so a 20 MB file on a slow uplink fails halfway. File transfers get their own 120 s
timeout. Also `answer` (`api.rs:171`) computes `retry_after * 1000` unchecked: a hostile or
broken answer overflows (panic in debug, wrap in release). It saturates and is clamped to one
hour.

## Touch only these paths
- `v3/crates/alexia-gateway/src/channels/telegram/api.rs`   (change)
- `v3/crates/alexia-gateway/tests/telegram_api.rs`   (change)

## Must not touch
`channels/telegram/mod.rs`, `channels/mod.rs` (P1-10), `gateway.rs` (P1-23), `ask.rs`,
`voice.rs` (P1-12), `Cargo.toml`.

## Interfaces
No public signature changes. New private constants in `api.rs`:

```rust
/// Whole-body timeout for file uploads and downloads (up to FILE_MAX on a slow link).
const FILE_TIMEOUT: Duration = Duration::from_secs(120);
/// The longest wait a 429 may ask for; longer answers are clamped.
const RETRY_AFTER_MAX_MS: u64 = 3_600_000;
```

`Error::RateLimited { retry_after_ms: u64 }` is unchanged.

## Steps
1. `upload` (`api.rs:290`): `.timeout(FILE_TIMEOUT)`.
2. `download` (`api.rs:351`): the file GET uses `.timeout(FILE_TIMEOUT)`. The `getFile` call
   before it stays on `CALL_TIMEOUT` (it goes through `call`).
3. `answer` (`api.rs:171`): `retry_after_ms: answer["parameters"]["retry_after"].as_u64()
   .unwrap_or(1).saturating_mul(1000).min(RETRY_AFTER_MAX_MS)`.
4. Tests below. In `tests/telegram_api.rs`, add a delay to the fake: rename the body of `fake`
   to `async fn fake_slow(route: Route, delay: Delay)` with
   `type Delay = Arc<dyn Fn(&Seen) -> Duration + Send + Sync>;`, sleeping `delay(&seen)` before
   writing the answer, and make `fake(route)` call `fake_slow(route, Arc::new(|_| Duration::ZERO))`
   so every existing test is unchanged.

## Tests
In `v3/crates/alexia-gateway/tests/telegram_api.rs`:
- `status_429_huge_retry_after_is_clamped`: answer 429 with
  `"parameters": {"retry_after": 18446744073709551615u64}` → `send_message` gives
  `Error::RateLimited { retry_after_ms: 3_600_000 }` (and does not panic).
- The existing `status_429_is_rate_limited_with_ms` still gives 7000.
- `voice_upload_outlives_the_call_timeout`: the fake answers `sendVoice` with `sent()` after
  16 s → `send_voice` returns `Ok(77)`. Fails on the old 15 s timeout.
- `download_outlives_the_call_timeout`: `getFile` answered at once with a `file_path`, the
  `/file/bot…/<path>` GET answered after 16 s with a few bytes → `download` returns `Ok` and the
  file holds those bytes.

- The two 16 s tests run in parallel inside one test binary, so they add ~16 s, not 32 s. Do
  not use `tokio::time::pause`: the crate has no `test-util`, and paused time with real sockets
  fires timeouts early.
- Use the token from `token()`; no other credential shapes (STATE.md builder rule).
- `get_updates` (the long poll) keeps its own `timeout_s + 10` timeout; leave it.
