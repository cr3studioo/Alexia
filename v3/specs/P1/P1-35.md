# P1-35: Time the bridge's save; faster commits in WAL mode

Model: opus
Depends on: none
Feature IDs: SP-09 (spans account for a turn's time)

## Goal
P1-18's end-to-end test found that `alexia-hub latency --check` intermittently fails a task turn
with "~385 ms unaccounted": `V2Bridge::reply` (alexia-hub/src/bridge.rs) calls `self.save(..)`
(two SQLite appends) after the `bridge` span ends, and nothing records that time. On this PC a
commit sometimes takes 200–400 ms (chat turns already show it in their `store` span), because a
WAL database still fsyncs on every commit at SQLite's default `synchronous = FULL`. After this
task the save has its own `store` span, and a WAL store runs at `synchronous = NORMAL`, the
standard setting for WAL: the database cannot be corrupted by a crash or power loss, and at most
the last moments of commits before a power loss are lost.

## Touch only these paths
- `v3/crates/alexia-hub/src/bridge.rs`   (change: a span around `save` in `reply`, plus its unit test)
- `v3/crates/alexia-store/src/db.rs`   (change: `synchronous = NORMAL` when `wal`)

## Must not touch
`alexia-hub/tests/telegram_e2e.rs` (P1-18 owns it), `alexia-core` (the `Span` type and chat.rs's
own `store` span are fine as they are), migrations, any other crate.

## Interfaces
No new public items. Existing: `alexia_core::Span::since(name, began, from)` records a span from
`from` until now, offset from `began`. Chat turns already use the name `"store"`
(alexia-core/src/chat.rs:289); reuse that name so the dashboard groups them together.

## Steps
1. In `V2Bridge::reply`, take `let storing = Instant::now();` right before `self.save(..)`, and
   after a successful save push `Span::since("store", began, storing)`. The span must be in
   `st.spans` before the `Reply` is built, so it is recorded with the turn. A save that fails
   still returns its error as today.
2. In `Store::init` (db.rs), inside the existing `if wal { .. }` block after the journal-mode
   check, set `conn.pragma_update(None, "synchronous", "NORMAL")?`. In-memory stores are
   unchanged.
3. Tests:
   - bridge.rs unit test `save_has_a_store_span`: with the existing fake v2 helpers in that test
     module, a task reply that writes words has a span named `store`, starting at or after the
     `bridge` span's end. Use the module's existing reply test as the model.
   - db.rs `#[cfg(test)]` unit test `wal_store_uses_synchronous_normal`: open a file store in a
     temp dir and read `PRAGMA synchronous` through the store's own connection: it is 1 (NORMAL).
     `PRAGMA synchronous` is per connection, so a second `Connection` would not show it.

## Tests
`save_has_a_store_span`, `wal_store_uses_synchronous_normal`, and
all existing tests unchanged.

- Don't change the 5% rule in `latency --check`; the fix is that the time is accounted for.
