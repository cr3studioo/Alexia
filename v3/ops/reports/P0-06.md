# P0-06 report: Store: secrets in Credential Manager

Status: done

What I built:
- `alexia_store::secrets::{get, set, delete, delete_all}` with service `alexia` and account `<owner>.<key>`. The owner must match `^(_core|[a-z][a-z0-9-]*)$` and the key must pass `is_ident`, or the call returns `Error::Invalid`. The Invalid messages never repeat the owner or the key.
- `get` turns "no entry" into `Ok(None)`, and `delete` treats a missing entry as Ok. A keychain failure returns `Error::Keychain("The system keychain could not be read/written/cleared.")`. The keyring error text goes only to `tracing::debug!`, and on `set` only if it does not contain the secret.
- `MEMORY_BACKEND_ENV` (`ALEXIA_SECRETS_IN_MEMORY`) switches to a `LazyLock<Mutex<HashMap>>` in the process.
- keyring features: `keyring = "4.2"` with its default `v1` feature. That gives `windows-native-keyring-store` (Credential Manager) and `apple-native-keyring-store/keychain` (macOS Keychain), plus zbus Secret Service on Linux. The workspace already pinned `4.2` with default features, so it needed no feature change.

§8.7 keychain compatibility on Windows: **works, both ways.**
- v2 (`cross-keychain` 1.1.0 → `@napi-rs/keyring`) writes service `alexia`, account `_v3check.probe` to Credential Manager. The target is `LegacyGeneric:target=_v3check.probe.alexia`, with user `_v3check.probe`.
- keyring 4.2 on Windows uses the same target, `<account>.<service>`. `Entry::new("alexia", "_v3check.probe")` read `not-a-secret`.
- A v2-written `_core.v3check_probe`, read through the real `secrets::get("_core", "v3check_probe")`, returned `not-a-secret`.
- The reverse also works: a v3 `secrets::set` was read back by `cross-keychain`.
- Every probe entry was deleted afterwards (`cmdkey /list` shows no `v3check`). The probe scripts lived in the scratch folder and were not committed. cross-keychain was npm-installed there, because this worktree has no `node_modules`.
- macOS was not checked. That still needs a run on the Mac.

v2 vault: this PC's v2 desktop install did use it. Credential Manager holds `LegacyGeneric:target=_core.vault.dev.alexia.app`, user `_core.vault`. No other service-`alexia` plugin entries were found, so on this PC v2's secrets live in the vault that v3 does not read in P0.

Problems or doubts:
- The spec contradicts itself. Step 4 asks for `secrets::get("_v3check", "probe")`, and the unit test uses `_v3test.probe`, but the owner rule rejects both because of the leading `_` (only `_core` is allowed). I kept the rule. The unit test calls the keychain backend directly with account `_v3test.probe`, which also makes it ignore `MEMORY_BACKEND_ENV`. The compatibility read covers both routes described above.
- I added `tracing.workspace = true` to the crate's Cargo.toml, which the spec did not list. It is needed for the required `tracing::debug!`, and the dependency is already in the workspace.
- `get` failures are logged without a redaction check, because no secret is in hand. keyring's `BadEncoding` Display does not print the bytes.
