# P4-32: Gateway: notices and the conversation follow the owner

Status: done

What I built:
- `Follow`, `Gateway::set_follow`, `HANDOFF_MS`. A `Say` with `to: None` goes to the followed face only; if that send fails it goes to the primary chats as before. Urgent also reaches the messenger's primary chat.
- Handoff: one shared routing table (was one per poll task). A message from another face within 30 min moves the conversation's actor and session there; a running turn drafts and delivers there; the old face's draft is cleared and it gets "Continued on <face>."
- A face is the channel name, or the device id on "device", so two chats of one channel never merge.
- The same face keeps its conversation after any gap. A face the owner returns to from elsewhere after 30 min goes back to its own session. `/new` starts fresh on any face.

Problems or doubts:
- Urgent is coded as "primary chat of every non-device channel", not by the name "telegram": invariant check 1 forbids naming it in gateway code. Same behaviour today; a second messenger would get urgent notices too.
- P4-41 expects `Gateway::current_session` and `moved_to`. This spec lists neither, so they are not exposed (and `run` consumes the gateway): P4-41 will need a gateway change.
- P4-33: `route` treats every `from_owner` message as the owner's; guest messages must bypass the handoff there.
- The 30 min count from the owner's last message, not from the end of its reply, also while a long run is still going.
- "Continued on" is sent only when a turn is running (read from the spec's sentence), not on every face change.
- Only after a run longer than 30 min: if the conversation moves onto a face still running it, that run finishes and is recorded, but `/stop` no longer reaches it.
- Ack spans are keyed by message id alone; equal ids from two faces in one conversation could mix up timing rows only.
