# P4-18: device-notify: native notifications with a reply
Status: done

## What I built
- Tool `notify_show`, bound to `notify.show` on Windows and macOS: `{shown}`, plus `answer` (`{data?}`/`{text?}`/`null`) when buttons or reply are asked.
- Windows: WinRT toast from a constant PowerShell script; notice goes by stdin (base64 JSON), XML escaped in JS. PowerShell 5.1 cannot subscribe to WinRT events, so the script compiles a small C# handler (CodeDom; `Add-Type` rejects `.winmd`) in the same process.
- macOS: `osascript` JavaScript (`displayDialog` / `displayNotification`), notice as JSON on stdin, never in code or argv; low urgency is never a dialog.
- 60 s wait counted from when the notice is up (40 s limit to get it up); a Mac dialog is left open (at most 5); same `id` replaces; cancel closes the helper; notice text is never logged, stderr is discarded.

- macOS never run (script tested with stand-ins). Check on a Mac: the dialog does not activate itself (so it cannot swallow typing) and may open behind windows; `sound name "default"`.
- Spec says a later click is nothing; capabilities.md (P4-01) says a late answer reaches the hub as a face message. I followed the spec; the plugin posts nothing.
- Choices to review: "Close"/"Reply" buttons added when under three; with three buttons plus reply, typed text returns with `data`; only urgent has sound; shown:false is also `isError` so the hub can fall back.
- A runtime C# compile could be blocked by antivirus or policy: asking notices then return shown:false (plain ones do not compile).
- Outside my paths, untouched: plugins/device-clipboard sets no `_meta["alexia/provides"]`, and the v3 host (alexia-mcp host.rs `hosted`) binds only from that, so `clipboard.*` calls likely do not resolve.
