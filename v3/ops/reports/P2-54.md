What I built:
- `alexia.db.keyed` marker (fixed text, no key material), written and fsynced by `encrypt` before it stores the key.
- `Store::open`: a new path reads the keychain only when the marker exists. A plain file with a marker and a stored key opens plain, with one warning that `alexia-hub encrypt` will finish it. Once an encrypted file opens with the right key, `alexia.db.plain` and its -wal/-shm are shredded, with one warning that names the file.
- `encrypt`: plain db + stored key + marker resumes with the stored key (refuses if it is not 64 hex digits); a stored key without the marker still refuses. Already encrypted + `.plain` beside it: shreds the leftover, then refuses. On a failure before the swap, a key this call made is deleted (key first), then the marker; a resume keeps both. `shred` is `pub(crate)`.
- `Store::live_touch` returns `Result<bool>` (true when a row matched); INTERFACES §2.1 updated.
- `Trace::resume` calls `live_touch` once and refuses on false (same sentence); `Trace::open` takes the start time: now for `begin`, the live row's `started_at` (read after the touch) for `resume`. The resume note and `RunStarted` keep the resume time.

Problems or doubts:
- new_store_reads_no_keychain uses no counter. It turns off the memory backend and puts a key in the `ALEXIA_SECRET__CORE_STORE_KEY` override, which `secrets::get` returns before it reaches Credential Manager. Old code then made the new store encrypted, so a plain result proves no key was read, and the real keychain is never touched. It restores the env vars through a Drop guard and holds LOCK.
- Shredding `.plain` on open happens only after the encrypted file opened with the right key. With the key missing, the leftover may be the owner's only readable copy, so it is kept (plain_leftover_kept_while_key_is_missing). `encrypt` shreds it on its "already encrypted" refusal without checking the key, as the spec says.
- Only `alexia.db.plain-wal`/`-shm` are shredded on open, not `alexia.db-wal`/`-shm`: those may belong to the encrypted database.
- The marker stays after a successful encrypt, so a deleted database is recreated encrypted (the old behaviour while a key was stored).
- Commit 11a3cb9 (live_touch/trace) also carries db.rs's open() change. That change only works with commit ebb5f4a, so review the two together.
