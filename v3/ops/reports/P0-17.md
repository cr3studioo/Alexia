# P0-17 report

Status: done (one spec test skipped by coordinator decision, see below)

What I built:
- `McpHost::purge` now calls `set_enabled(false)` first, so the plugin is stopped and a late
  call is refused as switched off instead of respawning it.
- `purge` keeps going when deleting keychain secrets fails: it logs a warning (error text
  only, no secret values), removes the own dir and cache, then returns the keychain error.
- `alexia/settings/get`: a stored JSON null falls back to the manifest default (v2 `??`).
- Removed `installed_at()` and its `_core/provenance` read; capability ties go to the lowest
  plugin id (the plugin map is a BTreeMap).

Problems or doubts:
- `purge_finishes_when_keychain_fails` is NOT written. There is no way to make a secret delete
  fail: the in-memory backend never fails, and manifest validation rejects every id or key that
  would make `account()` fail. Adding a switch means touching alexia-store, which is outside
  this spec. The coordinator chose to skip the test. The carry-on path is about 8 lines in
  `purge` and has to be checked by reading it. A follow-up could add a test-only delete
  failure switch to `alexia_store::secrets`.
- If `store.purge` itself fails, purge still returns early and leaves the folders behind,
  as it did before. The spec only covers the keychain case.
