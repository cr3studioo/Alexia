Problems or doubts:
- v3 `McpTooling::call` returns text only (no structuredContent), so plugin rows are parsed from the result's JSON text (`{rows:[...]}`, `{nodes:[...]}` or a bare list). MCP servers that return structuredContent also send it as text, which this relies on. Numeric row ids are turned into strings.
- Plugin rows/detail are gated like v2 (an undeclared rows tool asks first). They are not audited; only button presses are.
- The router has no single pin. `use_model`/`set_order`/`automatic` write the pin list for chat, plan, step and code. One entry shows as "Your choice", several as "Your list".
- Data v3 lacks gets placeholder values: prices "free", tier "T1", week "—", set-aside reason generic, `via` text generic. The library list shows installed plugins (what v2 surface.ts does), not a registry cache as the spec wording suggests.
- Core does not check skill consent, and `Skills` loads once at start. A skill can show "waiting for your yes" while the model can still read it. A newly learned skill is not seen by the model until the hub restarts.
- v3 run bodies have no `task`. Activity takes it from the session's last user message before the run, else the tools used.
- The action response has no `panes` (v2 added them; that is plugins-area work).
- `/api/learn forget` returns ok:false for a folder that does not exist (v2 said ok). It also clears that skill's consent.
