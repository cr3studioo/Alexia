# P4-24 report

Status: done

What I built:
- `socket.js`: RFC 6455 server on `node:http` upgrade, bound to 127.0.0.1 (remembered port, falls back to any free one if taken). Text frames only, fragments reassembled, ping/pong, 4 MiB cap checked from the frame header (close 1009), unmasked/RSV/binary frames closed. Gates: Origin must be `chrome-extension://<id>` or `extension://<id>` (403 otherwise); id pinned on the first valid hello (another id gets 403); one connection at a time (409); first frame must be `{"hello":1,token}` checked with `timingSafeEqual`, else close 4001 "bad token" (also after 10 s of silence).
- `pilot.js`: numbered requests, 15 s timeout, disconnect fails pending calls. Tools `browser_tabs/read/open/click/fill` (each bound to its capability via `_meta`) plus `browser_focus` (unbound). Results are rebuilt field by field from a whitelist, so cookies and existing field values cannot pass through; `fill` only acknowledges; `read` text clipped to 200 KB on a character boundary; `open` accepts only http/https.
- `index.js`: token (32 random bytes, base64url) kept in kv and shown via the `token` status; `port` status; `browser_new_token` tool. Token and page text are never logged.
- `plugin.json`: `lifetime: resident` (it holds a listener), `net.listen` reason names 127.0.0.1, settings: `token` status, `new_token` action, `port` status.

Problems or doubts:
- `browser_new_token` also clears the pinned extension id. Without that, reinstalling the extension (new id) would lock the owner out for good. Reviewer: confirm that is wanted.
- `browser_focus` is not in the spec's tool list, but `focus` is in the protocol, so I added a tool for it without a capability binding.
- The token is shown as a status value, as the spec says. Anyone who can read the settings screen can see it.
- While one connection is open, a second is refused (409), even from the pinned extension. A half-open socket would block reconnecting until TCP notices it is dead.
