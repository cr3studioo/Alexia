# P2D-17 report

Status: done

What I built:
- windows.js `front()`: `{ pid, name, title }` of the foreground window (GetForegroundWindow + GetWindowThreadProcessId + GetWindowText, same PowerShell P/Invoke). For a UWP frame it gives the hosted app's pid, not ApplicationFrameHost's.
- UWP rule in C# `Owns`: a window counts as the target's when its own pid is the target, or when it belongs to ApplicationFrameHost and its `Windows.UI.Core.CoreWindow` child belongs to the target. The guard (`FrontIs`) and `focus` both use it. `focus` falls back to the hosting frame (`FrameOf`) when the target has no top-level window of its own.
- task.js `following(desktop, signal, start)`: holds the task's target pid. `open_app` re-targets to the opened pid and focuses it; `open_url` re-targets via `desktop.front()`. If neither knows a pid, the target does not change. run_task (index.js) uses it for look/press/click/type/key/notes/lastRun.
- replay.js: `replay(plan, { pid })` keeps a target that `focus` and `open_app` steps update. type/key/click pass the step's own pid, or else that target. With neither, no pid is passed, as before.
- Coordinator extra: click/scroll `TypeNotFound`. Cause: `-UsingNamespace System` repeated Add-Type's own `using System;`, a warning that Add-Type treats as an error. So `[Mouse]` was never created, and this happened every time I ran it. Now one shared `MOUSE` block (`[Alexia.Mouse]`, no extra using, `$ErrorActionPreference='Stop'`).
- windows.js `openApp`: the pid now comes from `Start-Process -PassThru` + `WaitForInputIdle`. The old window-title search gave up before Character Map had a window, which left the plan with no target. A launcher that exits (calc.exe) still falls back to the name search. A missing app still rejects.
