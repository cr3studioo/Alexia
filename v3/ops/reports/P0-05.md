# P0-05 report

Status: done

What I built:
- `namespace.rs`: an `impl Store` block with create_tables, insert, select, update, delete, count, raw, purge.
- Names: ns checked against `^[a-z][a-z0-9-]*$`, table/columns by `is_ident`, then double-quoted;
  physical name `p_<ns with - → _>_<table>`. Every value is a `?` parameter, including LIMIT/OFFSET.
- create_tables records the tables in kv `_core` / `tables:<ns>` (sorted, deduplicated JSON array).
  Every other call refuses a table missing from that record with `OutOfNamespace("<table> is not one of this plugin's tables.")`.
- insert/update add columns from the JSON type (integer/bool INTEGER, other number REAL, else TEXT);
  `rowid` in an insert, an empty row, an empty `set` or an empty update/delete `where` → `Invalid`.
- `where` compiles to an AND of =, !=, <, <=, >, >=, IN, LIKE, IS NULL after `Operator::validate()`; unknown column → `Invalid`.
- purge: one transaction that drops the recorded tables, deletes the record, then kv and settings for the plugin.
- raw: always `OutOfNamespace("Raw SQL is not available.")`.

Problems or doubts:
- Spec step 5 says to parse JSON text "as v2 does", but v2's `select` returns object/array columns as raw
  text and never parses them. I followed the spec and its test (`o` comes back as `{"k":1}`), so a plugin
  string that happens to be valid JSON starting with `{`/`[` comes back parsed. Confirm this before P0-07/P0-13.
- v2 returns empty/0 for a declared table that has no columns yet. Here that case already works because
  `rowid` is a real column, but a `where`/`order` naming a column that was never written is `Invalid` (as the spec says), not empty.
- `ns` `a`/table `b_x` and `ns` `a-b`/table `x` map to the same physical table. The record keeps purge
  correct, but two such plugins would share rows. Refusing that at create time may be worth adding.
- Updating with a `set` that contains `rowid` is allowed, as in v2.
