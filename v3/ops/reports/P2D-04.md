What I built:
- `alexia-api/src/state.rs`: the routes behind INVENTORY A1–A7, ported from v2 serve.ts. They are `/api/state`, `/api/setup`, `/api/permissions`, `/api/ceilings`, `/api/adult`, `/api/panels` (v2 `CORE_TABS`) and `/api/search` (`palette.ts` scoring with v2's `SETTINGS`, plugins, plugin settings and titled chats).

- v3 never pays (D-P2D-6): `spent`, `cap` and `today` are 0 and `cross` is false. A positive `daily` or `monthly` gets 400 `{ok:false, said:"Alexia v3 only uses free models."}`.
- A provider key goes to the keychain as `_core`/`provider_<id>`. It is never sent back in an answer, logged, or written to kv. `keyStored` only says whether one exists.

Problems or doubts:
- `tests/gate.rs` `bad_json_400` expected the 501 setup stub. With the coordinator's approval, it now only checks that the gate does not refuse the body (not 400 or 403).
- Saving a key does not wait for the provider's model list, so a key the provider refuses (401) is still stored. The catalog is refreshed in the background, and that refresh drops a refused provider. The answer says "still arriving".
- `mode` in `/api/setup` writes kv `_core/mode` directly. `local_models` has no transition request yet (P2D-09).
- `/api/ceilings` stores `steps` in kv `_core/ceilings` in v2's shape. The agent's `Limits.max_steps` does not read it yet (that is in alexia-core, which I may not touch).
- Provider ids with a dash (`kilo-gateway`, `cloudflare-ai`, `ollama-cloud`) are not valid keychain key names in v3 (`is_ident`). Saving a key for one answers 500. This is the same limit `free::key_for` already has.
- `who()` is cached for 30 s; v2 kept it until tools changed. Search leaves out runs, skills and tools (other areas own those lists).
