# P0-07 report: Store, the v2 importer

Status: done

What I built:
- `alexia_store::import::{ImportReport, import_v2, import_v2_files}`, matching INTERFACES.md §6.
- The checks run in the spec's order, and each refusal is a full sentence. The copy is opened
  read-write once for the checks and `wal_checkpoint(TRUNCATE)`, then `ATTACH`ed as
  `file:/C:/…?mode=ro`.
- One transaction: the core tables are copied using the columns both sides have (so an older
  v2 gets NULLs and defaults). Each `p_*` table and its indexes are created from
  `v2.sqlite_master`, then filled with `INSERT … SELECT *`. Bad message bodies are copied and
  listed in `skipped`. Unknown tables go in `skipped`. `attachment_leases` and `strikes` are
  left out.
- kv `_core` / `tables:<ns>`: the owner is the longest plugin id (from kv.ns, settings.plugin,
  `plugins/*` and `extensions/*`) whose `p_<id>_` prefix matches. A table with no match is
  still copied and listed as "not attributable".
- The `imports` row is written inside the transaction. After the file copy it is updated with
  `files` and the file skips.
- Files are copied, never moved: plugins/<id> → own_dir, extensions/<id>, skills, uploads.
  `cache/` is not copied. A file already at the destination is left alone and listed.

Problems or doubts:
- kv and settings use INSERT OR REPLACE, so v2's value wins over anything a fresh hub already
  wrote. The other tables use a plain INSERT, so a clashing ledger id fails the whole import.
- If the hub already has a `p_*` table with a v2 table's name, the import is refused with a new
  sentence ("This hub already has a table named …"). §6 does not mention this case.
- A v2 row that breaks a v3 constraint fails the whole import with a raw SQLite error, not a
  sentence. Constraints v2 lacked: NOT NULL on kv/settings values, CHECK on messages.role.
- `import_v2_files` returns only a count (the fixed signature), so its per-file skips are not
  shown on its own.
- The `p_*` CREATE/INDEX SQL comes from the v2 file and is run with `execute`, which runs only
  one statement. Table names must match `^[a-z][a-z0-9_]*$`.
