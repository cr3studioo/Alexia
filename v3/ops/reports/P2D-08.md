# P2D-08 report: Library (plugins and skills from the shelf)

Status: done

What I built:
- `GET /api/library`: port of v2 `library.ts` (`plugins`, `skills`, `revoked`, `updates`, `offerable`, `readReleases`) and serve.ts 2650–2725. Two sources as v2: `github:owner/repo` releases (15-minute cache, kv `_core`/`shelf` fallback) and the static `/v0/` layout. A network failure answers v2's `{ok:false, registry, app, why}`.
- `GET /api/library/progress?id=`: `{done,total}` while downloading, else `{done:0}`.
- `POST /api/library/install`: fresh entry read (410 = withdrawn), revocation list, coming-soon refusal, version verdict, sha256 hashed while streaming (reqwest/rustls). Then unpacking: zip (`zip` crate) or tgz (`%SystemRoot%\System32\tar.exe`, CREATE_NO_WINDOW). Every entry is checked before anything is written; `..`, absolute paths, drives and links are refused. The plugin.json id must match the entry, then `McpHost::install_folder`. The plugin arrives disabled unless `enable`. An update replaces only the install folder, reloads, and turns the plugin back on only if it was on (or `enable`). A skill goes to `layout.skills()/<name>`, with `skill_preauth` and provenance written just before the folder.
- `ALEXIA_LIBRARY_REGISTRY`: a test seam that overrides kv `_core`/`registry`. v2 has no such variable.

Problems or doubts:
- Signatures: the workspace has no ed25519 crate, and Cargo.toml is not mine to change. So `verifying` is always false. A signed entry with no publisher key is "unverified", as v2. A signed entry *with* a publisher key configured is refused rather than passed as checked. Adding ed25519 later would restore v2's check.
- Provenance: the spec says `library`, but I recorded v2's word `installed`. The board's consent ladder (P2D-07) only knows v2's four values, and it records `installed` itself when it spends the preauth.
- Changes from v2 order, all safer: an update stops the plugin only after the download is verified (v2 stops it first). Preauth is written only after a skill is verified (v2 writes it before the download, so a failed install left a dangling yes). Preauth uses the skill's folder name, not the registry id.
- Hardening beyond v2: entries on the revocation list are filtered out of `plugins`, `updates` and `skills`, and refused at install. A skill name must pass core's skill-name rule before it becomes a folder name.
- The install response carries `{ok, said}` without v2's `panes`/`skills`: `plugins::panes` is private, and the UI reads only ok/said.
